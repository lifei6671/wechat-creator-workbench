# 稳定性与数据可靠性改造技术方案

## 1. 目标与实施边界

目标版本：下一稳定性迭代。审查基线：master 69a8b6187c5155d282ee7365584cefef4b446eb7。实施前以实际工作分支源码为准，复核相关调用链与已有测试。

保持 Tauri、React、Milkdown、Rust、SQLite、TypeScript 同步服务及 Workers/D1/R2、VPS 双部署模式。保留数据库作为正文事实来源、数据库云备份与完整工作区导出各自的语义，以及现有同步代际、游标、操作回执和版本冲突机制。

核心不变量：

- 已确认保存的正文必须可读；未确认保存的正文应有明确状态及尽可能短的持久化恢复窗口。
- 同步服务接受的有效实体必须能够由相应协议版本的客户端应用。
- 云端初始化可续传、可诊断、可恢复；不允许通过清除待同步记录伪造成功。
- 数据库快照的引用与素材清理生命周期应协调；恢复时明确缺失素材。
- 任何自动修复不得静默覆盖本地创作内容或远端更新。
- 所有数据库迁移保留旧数据，新增结构按现有迁移序列追加，禁止修改已发布迁移。

## 3. ST-01：同步协议一致性

### 3.1 涉及模块

- apps/sync-server/src/protocol.ts、sync.ts、app.ts
- apps/sync-server/migrations/ 中的依赖校验视图
- src-tauri/src/content/sync.rs、content.rs、content/collections/sync.rs、assets/sync.rs
- src-tauri/src/sync/contents.rs、contents/reconcile.rs

服务端对 entry.status、部分字段类型和 URL 等的校验弱于 Rust 客户端；非法记录可能被服务端接受而在全量恢复时使事务回滚。

### 3.2 数据契约

逐个实体类型建立字段契约清单，包含必填项、可空项、历史版本缺省值、枚举、长度和语义限制、关系约束。覆盖 entry、category、asset、collection、collection_node、collection_edge、wechat_publication_defaults。

以 Rust 实际反序列化、业务校验、SQLite 约束以及已发布协议为依据，保持旧客户端兼容。未知扩展字段按协议版本策略处理；不能把未来字段误判为损坏。正文内联及 blob 模式互斥，blob 校验同时覆盖大小、摘要、正文 UTF-8 可解码性；依赖检查包含资产、分类、来源和画布端点。对于无需下载的服务端附件，采用有界流式验证或在上传阶段记录已验证元数据；不得在数据库事务内发起网络调用。

建立共享 JSON 测试样本目录（例如 tests/fixtures/sync-contract），每个样本标注协议版本、预期接受/拒绝、稳定错误码。TypeScript 测试执行 operation() 和数据库约束，Rust 测试执行真实 hydrate/apply 路径。确保有效样本能往返，非法样本不产生实体、变更或成功回执。区分 HTTP 协议错误、业务拒绝与版本冲突。

### 3.3 已有异常数据

新增只读诊断流程，返回实体类型、ID、远端修订号、错误码和必要字段路径；日志默认不输出正文、令牌和凭据。已有增量组应用失败时继续使用事务保存点，保留原始组与依赖信息，标记阻塞原因。基线暂存区在校验通过后才正式应用；失败时保留暂存和本地状态，允许重新诊断或重试。不得跳过依赖不完整的组后宣告工作区一致。

服务端提供自托管管理员可执行的检查/修复流程，修复需生成正常的版本化变更或显式的新代际恢复，不能直接无痕修改历史。首版不强制开发复杂的管理后台。

部署顺序：服务端向后兼容校验与诊断 → 客户端错误提示和恢复 → 两端联调。若契约存在不兼容变化，单独设计协议升级和能力协商；不无条件提升协议版本。

## 4. ST-02：首次初始化与同步恢复

### 4.1 当前调用链

src-tauri/src/sync/contents.rs 中 exchange → queue_existing → stage_outbox → prepare_uploads → push_one → reject_outbox。失败记录进入 sync_issues，同代次可能不再入队，而初始化完成条件要求 sync_dirty 清空。服务端 seed_device 锁定初始化归属，其他设备等待。

### 4.2 状态与接口

保留服务端 empty/seeding/ready 三态；客户端通过持久化现有同步状态和问题记录派生 initializing、blocked、retrying、ready 等展示状态，不为纯 UI 状态重复建立业务状态表。

同步状态应显示：待上传数量、已拒绝数量、当前阻塞原因、最近成功时间、相关实体 ID、可执行修复动作。读取统计应通过聚合查询，禁止频繁传输全文。

错误分类：
- 临时网络/服务限流：保留冻结出站操作及 operationId，指数退避，显式重试可唤醒。
- 素材缺失或校验不匹配：保留本地引用，提供重新下载、从本地文件重新绑定或移除引用的入口。
- 元数据超限：指向具体实体及限制，编辑修复后按新代次重试。
- 版本冲突：沿用现有冲突处理，保持本地和远端数据可追溯。
- 设备身份变更：先核对旧操作回执，再按现有 reconciliation 流程处理。

修复动作事务化更新资产或正文、引用关系及 dirty generation；只清除已被修复的对应问题。不支持的冲突类型需给出明确可操作的诊断，不提供无效按钮。

### 4.3 初始化所有权恢复

优先复用现有 recovery key / 管理员设备恢复机制恢复原 seed_device，验证相同设备身份能继续上传。若无法恢复原设备，提供受控的管理员恢复路径：先检查服务端部分初始化数据及回执，明确是否可以接管；无法安全接管时导出或保留旧实例的数据后，通过显式新代际重新初始化。不要仅凭超时自动抢占 seed_device，也不要让两台设备并行初始化。

初次同步允许正常数据先完成上传，但只有全部必需依赖和待处理操作完成后才进入 ready。若用户确认放弃某素材，必须修改对应业务引用或保留合法的缺失素材占位，并确保服务端与客户端均认可该实体，不能只删除 sync_dirty。

验收：缺图、上传超限、断网、响应丢失、设备重装、初始化设备不可用、部分上传后退出、并发加入；每种场景均有明确状态和恢复路径。正常数据不重复写入，不发生静默丢失。

## 5. ST-03：编辑器异常退出恢复

### 5.1 范围

apps/desktop/src/editor/save-queue.ts、workspace/DesktopShell.tsx、packages/editor-react、src-tauri/src/content.rs、db.rs、commands.rs。保留现有 750 ms 防抖及 4 s 最大调度延迟，先验证当前分支 Markdown 源码编辑、所见即所得编辑与 AI 替换的快照契约。

### 5.2 数据模型

新增本地恢复表（具体迁移编号以实际 HEAD 为准）：

```sql
CREATE TABLE editor_recovery (
  entry_id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL,
  base_version INTEGER NOT NULL,
  local_revision INTEGER NOT NULL,
  fields_json TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);
```

fields_json 保存恢复所需的完整可编辑字段及正文；不保存 API 密钥、AI 凭据。session_id 使用跨进程唯一标识而非仅内存递增编号。正文恢复表不加入同步触发器或远端实体协议；数据库快照中保留恢复记录时应明确其仅供人工恢复，不在新设备自动覆盖正文。

IPC：editor_recovery_put、editor_recovery_list、editor_recovery_discard（名称为建议，遵循现有命名）。写入采用会话/修订条件更新，旧请求不得覆盖新快照；清理必须匹配会话和已正式保存的修订。正式保存与对应恢复记录清理尽量在同一 SQLite 事务中执行，旧保存完成不能删除更新的恢复草稿。明确处理旧会话重启后的恢复选择及新会话创建顺序。

### 5.3 调度

恢复快照与正式保存共用序列化结果，避免在同一输入周期重复序列化整个 Markdown 文档。目标恢复窗口 1 秒左右（正常负载下，以测试数据确认），不承诺断电零丢失。正常保存成功时可直接清除覆盖范围内的草稿；保存失败或版本冲突时继续允许持久化恢复草稿。恢复写入失败必须呈现未保存/恢复失败状态。

所有退出、切换文档、AI 应用、同步应用等路径仍遵循现有 flush 与版本校验。保留已恢复内容直到用户确认正式保存或放弃。

启动恢复：
- 数据库版本等于 base_version：展示恢复时间与正文差异，可恢复到原文档后执行版本校验保存。
- 数据库版本变化：保留正式内容与恢复稿，用户可比较并另存草稿；不得自动覆盖。
- 原文档已删除或永久删除：允许恢复为新文档，保持删除标记语义。
- 恢复稿与正式内容一致：可幂等清理。

验收：编辑后强制结束 WebView/应用、连续输入、大文本、IPC 返回乱序、正式提交成功但响应丢失、保存冲突、AI 替换、文档删除和重启恢复。确保恢复表在正常使用中不会持续累积。

## 6. ST-04：素材与备份生命周期

### 6.1 范围及策略

src-tauri/src/assets/cleanup.rs、assets/references.rs、assets/sync.rs、backup.rs、backup/store.rs、backup/restore.rs、backup/migration.rs。

保持云端数据库备份模式和完整工作区导出模式。数据库备份本身不等于图片备份；新设备恢复时，未曾上传且本地已不存在的素材无法凭数据库重建。UI 应提供素材可恢复状态与完整导出入口。

### 6.2 清理规则

将素材失去引用和物理删除分离。新增以 sha256 为键的本地候选记录（first_unreferenced_at、last_checked_at），重新被引用时移除候选。默认宽限期 7 天，覆盖当前 5 天云数据库备份保留策略；这是最小安全缓冲，不是完整备份保证。

清理保护集合包含当前正文、历史修订、回收站保留正文、专题截图与卡片正文、编辑器恢复稿、待同步/冲突/冻结操作依赖、保留标记以及仍有效的备份引用。使用现有素材引用扫描实现，避免重复维护两套解析规则。

清理执行前再次核验保护集合和工作区状态；远程删除与本地引用创建需由后端同一生命周期协调机制约束，避免仅在删除前查询一次造成竞态。复用已有上传 gate、退出阶段限制及事务；如果无法证明并发安全，首版只在已冻结写入的维护阶段执行物理删除。删除失败保留可重试任务，不提前清除位置记录。

公共发布图片属于外部长期引用：为已发布用途建立显式保护标记，自动清理仅处理可确认不再需要的对象。历史已上传但无法确认是否被外部文章使用的素材采用保守保护策略，不批量删除。

### 6.3 备份引用保护

为新增数据库备份生成与实际 SQLite 快照一致的素材哈希清单（可选旁路 manifest，包含 workspace_id、snapshot_id、哈希列表及创建时间）。清单与快照的发布顺序和清理顺序必须避免快照有效但引用保护未生效。备份失败、清单缺失或旧格式快照存在时采用保守处理；不得根据本机缓存猜测远端全部有效备份。

多设备共享对象存储时，本地宽限期不能单独保证远端删除安全：公共对象自动删除需得到所有有效备份及发布引用的可靠证据，否则只允许清理本地可再获取缓存或人工确认删除。第一批可仅实现延迟清理与保护集合，并将跨设备远端物理回收延后。

恢复后进行素材完整性检查，分类为本地可读、可从同步服务获取、可从图床获取、缺失、校验失败。按需恢复且校验 SHA-256；摘要展示问题数量，允许按文章定位与重新绑定。禁止因单张图片缺失自动回滚已成功恢复的正文数据库。

验收：恢复五天前快照、历史修订引用、删除后重新引用、共享哈希、跨设备恢复、缺失清单、远端删除超时、公共发布图片、完整导出/导入。以本地文件及对象实际可读性为准。

## 8. ST-06：同步历史与附件容量治理（后续）

当前 sync_entities、sync_changes、sync_operations、sync_blobs 生命周期不同。先采集行数、字节量、最老游标、附件总量、变化趋势及失败操作数；确认现有管理脚本是否已实现部分清理。

建立设备确认水位或可过期设备策略；历史压缩按完整变更组处理，原子推进 min_cursor，旧客户端走现有 bootstrap/reconcile。全量读取与增量补偿期间需有保留租约或明确重试策略，避免压缩删除所需历史。回执保留期必须覆盖离线设备冻结操作恢复窗口；回执过期不能被解释为从未提交。保留必要删除标记，防止旧设备复活已删除内容。

blob 回收基于当前实体、保留历史、有效暂存操作和上传租约的可达集合，采用标记及宽限期、再次确认后删除。跨数据库与对象存储失败需可重试。先交付 dry-run 清单与容量报告，再启用受控回收。

验收：两设备长期离线、压缩期间全量恢复、同哈希共享、上传未提交、响应丢失、压缩后回执查询、删除标记恢复。保持原有数据协议上限。

## 9. ST-07：大型目录与画布批量操作（后续）

现有约束：单组 256 实体、请求 1 MiB、实体元数据 512 KiB、blob 25 MiB。保留限制，先改善用户可执行的错误提示，再实现持久化批量任务。批次必须依据真实序列化字节及依赖图划分。

目录删除：先迁移或处理子项，再删除父目录；画布删除：先删除边，再删除节点，最后删除专题。跨批次操作不再具备整体原子性，必须显式展示进行中状态、禁止不安全并发修改、支持断点续作及失败恢复。任务不自动撤销其他设备的后续变更。

验收：1000 条目录内容、256/257 边界、超大元数据、断电重启、另一设备同时新增子项、取消任务。验收结果应说明部分完成的可见语义。

## 10. ST-08：模块边界与性能

DesktopShell.tsx 优先提取文档会话（含保存队列）、同步协调、退出/恢复三个业务模块，组件保留布局与组合职责。以状态所有权和副作用生命周期作为拆分标准，不引入新状态管理框架；保留现有行为测试。同步核心逐步提取 transport、outbox/inbox、bootstrap、apply 等模块，复用 merge/reconcile/scheduler。拆分与功能修改分开提交。

SQLite 继续使用现有 Workspace、WAL 与事务机制。先观测互斥锁等待、事务耗时、索引积压、同步队列深度和编辑器序列化耗时；日志默认不含正文。压测 1 万条文章、1000 条目录内容、100 KiB/1 MiB 正文、同步与编辑并行。记录 p50/p95/p99、内存、IPC 字节及失败率，以同机器同数据集的现有版本为基线。建议目标：普通保存 p95 不超过 200 ms（不含防抖）、交互无持续明显阻塞、恢复窗口正常负载下约 1 秒；若不能达到则报告瓶颈并调整方案，不以虚构结果通过验收。

只有实测证明读取竞争严重，才评估单写连接与独立只读连接；恢复、迁移及关闭期间必须统一回收连接。

## 11. 执行及交付顺序

1. 检查工作树和最新迁移，确认已有实现与本方案的差距；为 ST-01、ST-02 编写复现测试。
2. 批次 A：协议契约、初始化恢复、CI 拆分；完成双端测试与兼容性验证。
3. 批次 B：编辑器恢复、素材延迟清理与备份检查；完成强制退出及恢复场景测试。
4. 稳定性发布：验证旧工作区升级、两端同步、完整导出/导入及实际桌面烟雾测试。
5. 批次 C：先完成容量和性能观测，再按实际瓶颈实施日志压缩、批量任务和模块拆分。

每批交付：变更文件、迁移影响、实际执行的测试及结果、未执行项目与原因、复现步骤、已知边界及回滚/恢复方式。新迁移不通过手工降低 schema 版本回滚；使用迁移前快照与兼容客户端恢复，验证恢复流程。服务端升级前保留数据库与对象存储一致的恢复点。

稳定性发布门槛：所有适用 CI 任务通过；已知 P1 复现测试通过；旧版本升级与双客户端故障注入通过；未验证的真实云端或平台场景明确列为发布阻塞或经维护者确认的例外。

## 12. 后续产品迭代

稳定性版本完成后优先建设公众号发布前质量检查、选题池与创作任务、写作风格管理及历史资料检索。运营数据导入和文章表现分析作为独立业务模块，先支持本地导入公众号导出的数据与文章匹配，再考虑 AI 选题建议。多维表格和插件体系根据实际创作需求排期。
