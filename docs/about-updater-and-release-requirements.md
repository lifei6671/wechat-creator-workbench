# 关于页面、应用更新与 Release 发布需求

状态：已开始实现。独立关于页、应用更新、版本注入、开源清单及发行流水线已落地；实际发布和三平台安装升级验收尚未进行，操作方式见 [发行指南](./release-guide.md)。

日期：2026-11-20。

范围：关于页面、发行版本注入、应用内更新、开源组件信息、桌面与同步服务端的 GitHub Release 发布流水线。

本文整理用户已经提出及后续补充的需求。用户已授权实现关于页、应用内下载和安装、Release 配套，但暂不发布。实现采用下述建议中的独立内容页、`vX.Y.Z` 稳定渠道和 Mac 官方应用内替换与重启方案；首发版本与 Windows 系统代码签名仍留到正式发行时确定。第 2 节为实现前的仓库快照。

## 1. 需求概览

| 项目 | 要求 |
| --- | --- |
| 关于入口 | 在设置导航中增加“关于” |
| 页面独立 | 关于使用独立内容页，不追加到现有设置表单的连续滚动区域中 |
| 当前版本 | 显示正在运行的应用版本，版本号在 Release 构建时写入应用 |
| 检查更新 | 用户可以检查是否有适用于当前平台的新版本 |
| 下载更新 | 发现新版本后可以下载安装或更新包 |
| 安装更新 | 下载完成后提供安装入口，安全结束当前应用并交接安装；Mac 平台方案见第 5 节 |
| 开源组件 | 展示应用使用的开源库名称和实际版本 |
| 发布触发 | 推送发行标签后，由 GitHub Actions 自动构建并发布 GitHub Release |
| 平台 | macOS Intel、macOS ARM64、Windows x64 |
| 产物命名 | 使用 `CreatorWorkbench-版本-系统-架构` 作为文件名主体，保留实际文件扩展名 |
| NSIS 安装体验 | 安装与卸载向导使用简体中文，安装程序与安装后的应用使用应用自己的图标 |

| 更新记录 | 每次 Release 详细填写本次更新记录，不能仅列提交标题或套用泛化发布文案 |

本稿建议首版只提供手动检查、下载和安装正式版本，不增加启动时自动检查、定时下载、强制更新、增量更新、自动降级、Linux 桌面客户端构建或独立更新服务。VPS 同步服务端的 Linux 部署属于本次范围。

## 2. 当前仓库情况

以下为编写本文时检查到的现状，用于约束后续实现：

- 桌面应用使用 Tauri 2、React、TypeScript 和 Rust。
- `package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json` 中的应用版本目前均为 `0.1.0`。
- `SettingsDialog` 当前把设置分类渲染为连续滚动的多个表单区块，导航通过滚动定位。因此，关于页需要专门的独立页面分支，不能只在现有分类数组中追加一个表单区块。
- 现有退出流程包含文稿和画布保存、后台任务停止、素材清理及最终退出，需要在更新安装时复用相应生命周期。
- 关闭窗口默认可以收起到托盘。更新安装必须执行真正退出，不能被“关闭到托盘”设置替代。
- 现有 `.github/workflows/ci.yml` 在 master 推送和 PR 时运行检查，桌面构建使用 `--debug --no-bundle`，尚无标签发行打包流程。
- 当前未接入 Tauri updater。现有 `third-party-ai.txt` 已随应用打包，但不是全应用的依赖版本清单。
- 同步服务端位于 `apps/sync-server`，当前应用包版本同样为 `0.1.0`；`npm run build` 通过 TypeScript 编译生成 `dist`。
- Cloudflare 入口为 `src/cloudflare.ts`，使用 D1 和 R2；VPS 入口为 `src/node.ts`，使用 Node.js、`better-sqlite3` 和本地文件。两者共用协议、业务逻辑及 SQL 迁移，但入口、运行时和部署依赖不同。
- 现有服务端 Dockerfile 会复制 TypeScript 源码并在镜像构建时编译；面向已编译发行包时，需要配套提供直接消费编译产物的部署文件。

## 3. 关于页面

### 3.1 导航与布局

1. 在设置导航中增加“关于”，建议放在导航底部。
2. 点击后，设置窗口右侧切换为关于专页；页面内容只包含应用信息、版本更新及开源组件。
3. 关于页不使用现有配置表单布局，不出现通用设置、同步、图床等表单内容；滚动关于页时也不能滚到这些表单。
4. 保留设置窗口已有的标题、关闭入口、键盘操作和导航框架，不另开一个操作系统窗口。
5. 在关于与其他设置之间切换时，保留本次设置会话中的表单输入和原有滚动位置，不能因为页面独立而丢失未提交内容。
6. 设置搜索可匹配“关于”“版本”“更新”“开源”等入口关键词；关于页不参与普通设置表单区块的滚动定位计算。

视觉遵循 `docs/ui-design-guidelines.md`：使用 Radix 颜色与现有字号层级，避免新增大卡片、装饰性说明和重复按钮。

### 3.2 页面内容

按优先级展示：

1. 应用名称和当前版本。
2. 当前平台与架构，便于确认安装包类型。
3. 更新状态及当前步骤所需的主要操作。
4. 项目仓库和当前版本的发布说明入口。
5. 开源组件清单。

版本和组件信息为只读内容，不提供用户编辑版本号或更新源的表单。

## 4. 版本来源与写入规则

### 4.1 发行版本

- 建议发行标签采用 `v<major>.<minor>.<patch>`，例如 `v1.0.0`；应用内和产物文件名使用去掉 `v` 的 `1.0.0`。
- 发行构建以标签解析得到的版本为唯一来源，不要求每次发布前人工修改多处版本。
- 在 CI 临时构建工作区中，将版本统一写入 Tauri 配置、根 `package.json`、Rust 应用包版本、同步服务端 `package.json`，以及相关锁文件中对应的本项目包记录。
- 只同步本项目版本及必要锁文件记录，不借此升级第三方依赖，不把生成的版本修改自动推回 master。
- 同一发行的三个桌面平台与两种服务端部署包必须使用相同发行版本、相同标签提交和对应的依赖锁定来源；服务端包内提供版本信息和客户端协议兼容说明。
- 打包前校验注入结果；版本缺失、格式错误或各处不一致时终止发布。

### 4.2 应用显示

- 关于页通过原生应用元数据读取正在运行的版本；不能把 GitHub 最新版本当成当前已安装版本。
- 应用内版本、安装包版本、Release 版本、更新清单版本和产物文件名必须一致。
- 普通本地开发构建读取本地配置版本，不依赖 GitHub 网络请求才能显示版本。
- 下载新版本后，当前版本仍显示旧版本；安装成功并启动新应用后，才显示新版本。

`1.0.0` 仅作为本文示例，不代表已经决定首个正式发行版本。

## 5. 检查、下载与安装更新

### 5.1 更新来源与基础方案

建议使用项目现有 GitHub 仓库的 Release 承载安装包、更新包及更新清单，复用官方 Tauri updater；首版不自建更新服务。官方插件支持检查更新、分别下载和安装，以及下载进度回调，可承接“先下载、稍后安装”的交互。[Tauri updater 文档](https://v2.tauri.app/plugin/updater/)

更新匹配当前应用构建的系统与架构，不能只根据机器 CPU 猜测安装包。例如 Intel 版 Mac 应用在 ARM 设备上运行时，首版仍按当前 Intel 构建匹配更新，不额外做架构迁移。

### 5.2 用户操作流程

| 状态 | 展示内容 | 主要操作 |
| --- | --- | --- |
| 未检查 | 当前版本 | 检查更新 |
| 检查中 | 正在检查更新 | 禁止重复检查 |
| 已是最新 | 已是最新版本 | 检查更新 |
| 发现更新 | 可更新版本、发布说明入口 | 下载更新 |
| 下载中 | 实际下载进度；总量未知时显示已下载大小 | 展示下载状态，禁止重复下载 |
| 下载完成并通过校验 | 新版本已准备就绪 | Windows 为“退出并安装”；Mac 文案随第 5.4 节方案确定 |
| 安装准备中 | 正在保存并准备更新 | 禁止重复安装 |
| 检查或下载失败 | 明确失败状态 | 重试当前步骤 |

补充规则：

- 只有远端版本高于当前版本时才提示升级，不按字符串排序比较版本，不自动降级。
- 首版只消费正式发布且产物完整的稳定版本；草稿和预发布版本不进入默认更新入口。
- 用户选择安装前，不因发现或下载更新而主动关闭应用。
- 关闭关于页、切换设置页或收起设置窗口不丢失本次应用会话中的下载进度及就绪状态。
- 下载完成后允许继续工作，稍后返回关于页安装；跨应用重启恢复下载、断点续传不纳入首版。
- 网络失败、缺少当前架构产物或校验失败不能显示“已是最新版本”或进入安装状态。

### 5.3 安全退出与安装交接

1. 安装必须由用户点击明确触发。
2. 先完成全部文稿、专题画布和现有待保存操作的保存，再进入安装交接。
3. 复用既有任务停止、退出准备和素材清理规则；保存失败或用户取消退出时，保持应用可操作，不启动安装。
4. 更新安装使用明确的退出意图，绕过关闭到托盘行为，保证当前工作进程最终结束。
5. 不能直接先调用当前会立即结束进程的 `finish_exit`，再尝试从已经退出的应用启动安装器；最终退出步骤必须与原生安装交接协调。
6. 安装器启动前发生错误时，在应用中反馈；安装器接管后的错误由安装器报告。下载成功不等于安装成功，再次启动时以实际运行版本确认结果。
7. 更新不得主动清除数据库、素材、界面偏好或系统凭据；新版本的数据迁移沿用项目既有机制。

### 5.4 平台差异，待评审确认

| 平台 | 建议行为 |
| --- | --- |
| Windows x64 | 使用 NSIS `.exe` 安装器；完成保存和退出准备后交接安装，确保安装器在旧进程结束后替换文件；安装后可启动新版应用 |
| macOS Intel / ARM64 | 在无需 Apple 开发者账户的条件下使用 ad-hoc 签名构建；建议使用 Tauri 专用更新包替换应用并重启，DMG 用于首次或手动安装 |

Mac 的应用内更新包是 `.app.tar.gz`，Windows 可以复用安装器作为更新产物。这与“退出后打开 DMG，再由用户手动拖动安装”是不同体验。[Tauri 更新产物说明](https://v2.tauri.app/plugin/updater/#building)

本稿建议 Mac 采用官方应用内替换与重启流程。如果“退出后启动安装程序”在 Mac 上也必须严格表现为打开 DMG，则需在开发前确认采用手动安装路径，并同步调整按钮文案与验收条件。

Mac 无账户分发已确定，不再作为待确认项。ad-hoc 签名、首次启动与升级后的系统放行边界见第 7.4 节；更新方式需要在这个约束下完成实际验证，不能假设有 Developer ID 或公证凭据。

### 5.5 更新包验证

- 正式更新使用 HTTPS；更新清单中的链接对应本次发行的最终文件名和版本。
- 安装前必须完成 updater 签名验证；缺失或错误签名不能绕过。
- 更新公钥随应用发布，私钥只用于发行签名并存放在发布环境的 Secrets 中。Tauri 更新签名与操作系统的代码签名、公证是不同能力。[Tauri 更新签名说明](https://v2.tauri.app/plugin/updater/#signing-updates)

## 6. 开源库与版本清单

### 6.1 展示内容

关于页只展示 Tauri、React、Milkdown、Radix UI、React Flow、assistant-ui 和 rusqlite 等核心组件，显示名称和构建实际版本。许可证标识、项目链接及随附许可正文按需展开，不提供独立的“第三方署名”入口；完整直接与传递依赖清单和许可署名资料继续随应用分发。

核心组件使用紧凑列表，不提供搜索框或完整依赖总数，不逐个渲染为大卡片。

### 6.2 信息来源与范围

- 清单在构建时生成并随应用分发，断网时也可查看。
- JavaScript / TypeScript 组件使用锁文件和实际构建依赖图中的解析版本，不展示 `^19.x` 等版本范围。
- Rust 组件使用 `Cargo.lock` 和对应目标的依赖图中的实际版本。
- 覆盖随桌面应用分发的直接及传递依赖；只用于测试或构建、没有随产物分发的工具不混入应用运行组件列表。
- 对打包器内嵌的第三方代码、额外资源、已有抽离代码及许可声明一并检查，不能只扫描两个直接依赖列表就称为完整清单。
- 相同库同时存在多个版本时分别展示；去重应依据生态、库名称和版本，不能仅按名称合并。
- 展示当前构建实际使用的信息，不在用户打开关于页时联网查询某个库的最新版本。
- 不手工维护一张容易过期的库版本表。现有 `third-party-ai.txt` 中的许可及署名需要保留，并与新清单正确关联。
- 两种服务端部署包分别附带其实际分发依赖的版本与许可资料；不得把服务端依赖误标为当前桌面进程加载的组件。

## 7. 支持平台与产物命名

### 7.1 构建矩阵

| 平台 | Rust target | 文件名中的系统与架构 |
| --- | --- | --- |
| macOS ARM64 | `aarch64-apple-darwin` | `mac-arm64` |
| macOS Intel | `x86_64-apple-darwin` | `mac-x64` |
| Windows x64 | `x86_64-pc-windows-msvc` | `windows-x64` |

首版发布两个独立的 Mac 架构包，不额外生成 Universal 包。Windows 首版提供 NSIS 安装器，不另加 MSI 和便携版。

### 7.2 文件名示例

| 用途 | 文件名，示例版本为 `1.0.0` |
| --- | --- |
| Mac ARM64 手动安装 | `CreatorWorkbench-1.0.0-mac-arm64.dmg` |
| Mac Intel 手动安装 | `CreatorWorkbench-1.0.0-mac-x64.dmg` |
| Windows x64 安装及更新 | `CreatorWorkbench-1.0.0-windows-x64.exe` |
| Mac ARM64 应用内更新 | `CreatorWorkbench-1.0.0-mac-arm64.app.tar.gz` |
| Mac Intel 应用内更新 | `CreatorWorkbench-1.0.0-mac-x64.app.tar.gz` |
| Cloudflare 同步服务端 | `CreatorWorkbench-1.0.0-sync-cloudflare.tar.gz` |
| VPS 同步服务端 | `CreatorWorkbench-1.0.0-sync-vps.tar.gz` |
| 更新签名 | 对应更新产物追加 `.sig`，例如 `CreatorWorkbench-1.0.0-mac-arm64.app.tar.gz.sig` |
| 统一更新清单 | `latest.json` |

命名中的 `CreatorWorkbench` 是发行文件前缀，不自动改变现有应用名称、应用标识或用户数据目录。更新清单保留固定文件名，供应用定位最新正式版本。

重命名必须与更新清单生成协调：清单引用重命名后的真实下载地址，签名文件与对应更新包一一匹配，不能只改 Release 附件名称而留下旧 URL。

### 7.3 NSIS 中文与应用图标

- NSIS 安装和卸载向导只启用简体中文，首次安装及覆盖升级均保持中文，不默认显示英文或弹出多余的语言选择步骤。
- 安装器、卸载器、安装后的应用和快捷方式统一使用本项目应用图标；Windows 图标复用 `src-tauri/icons/icon.ico`，不使用 Tauri 或 NSIS 默认图标。
- 安装器窗口、文件属性及系统应用列表中的产品名称和版本应与实际发行一致。
- 验收包含全新安装、覆盖升级和卸载，分别核对语言及图标，不能仅检查应用启动后的窗口图标。

### 7.4 Mac 无开发者账户分发

- 已确认没有 Apple 开发者账户。两种 Mac 架构均采用无需开发者证书的 ad-hoc 签名构建，不进行 Developer ID 签名和 Apple 公证，也不发布到 Mac App Store。
- 发布工作流不能要求提供 Apple 账户、Developer ID 证书、Team ID 或公证凭据；缺少这些配置不应使 Mac 打包失败。
- ad-hoc 签名不等于 Apple 认证。浏览器下载后的应用可能仍需用户在系统“隐私与安全性”中允许打开，发行说明必须提供相应的首次安装指引，不能承诺无系统提示。[Tauri ad-hoc 签名说明](https://v2.tauri.app/distribute/sign/macos/#ad-hoc-signing)
- 分别验证 Intel 和 ARM64 的首次打开，以及两个连续版本之间的应用内更新和重启。若升级后仍需系统放行，准确记录并在发行说明中说明；提供对应 DMG 的手动安装入口，不关闭系统安全功能或绕过更新包校验。
- Tauri updater 的更新签名继续保留。这套密钥由项目自行生成，与 Apple 账户无关，不能因为没有 Apple 账户而取消更新签名。

### 7.5 已编译同步服务端部署包

#### 产物是否合并

当前两种产物不一致，应发布 Cloudflare 与 VPS 两个服务端包。共用 TypeScript 业务代码或 SQL 迁移，不代表同一个编译入口能同时运行在 Worker 和 Node.js 中。

如果后续实现验证部署入口、编译结果与依赖均可共用，才考虑合并；将两套不同入口装进同一个压缩文件，不等同于“两种产物一致”。本稿按两个包设计，不额外发布包含相同内容的总包。

#### Cloudflare 包

包内至少包含：

- 已编译、已打包的 Worker JavaScript 和其运行所需模块。
- 指向已编译入口的 Wrangler 部署配置模板，保留 D1、R2 绑定及迁移目录声明。
- 完整 SQL 迁移文件、现有 Cloudflare 管理员恢复脚本及其工具依赖说明。
- 部署工具的依赖清单与锁文件、版本信息、开源许可资料和部署说明。

用户解压后配置自己的 D1、R2 与密钥，安装锁定的部署工具即可部署，不需要克隆完整仓库或再次编译 TypeScript。不能把仍指向 `src/cloudflare.ts` 的源码配置原样放进无源码的发行包。

#### VPS 包

包内至少包含：

- `dist/node.js` 及其依赖的全部已编译模块，保持模块与迁移文件所需的相对目录结构。
- 运行依赖清单与锁文件、完整 SQL 迁移文件。
- 直接使用已编译 `dist` 的 Dockerfile、Compose 配置及 `.env.example`。
- Node.js 运行方式、版本信息、开源许可资料及新装和升级说明。

解压后可以通过包内 Dockerfile / Compose 部署，也可以在符合运行条件的 Node.js 环境安装生产依赖后启动。部署时不得再要求 TypeScript 源码或 TypeScript 编译工具。

`better-sqlite3` 包含原生模块，生产依赖须在实际运行系统或容器中准备；不能将桌面 CI 机器上的 `node_modules` 原样当作跨平台运行依赖。这里的“已编译服务端”指应用代码已经编译为 JavaScript，不承诺打包成自带 Node.js 的独立可执行文件。

#### 部署与升级边界

- 服务端产物面向手动部署，桌面更新器只更新桌面应用，不自动替用户更新远端 Worker 或 VPS 服务。
- Cloudflare 升级继续复用原 D1、R2；VPS 升级继续复用原持久化卷，迁移按既有机制执行。
- 两包均不得包含真实 `.env`、部署密钥、账号私有配置、数据库、WAL 或用户素材。
- Release 中的 GitHub 自动源码压缩包不能替代这两个已编译部署包。

## 8. GitHub Actions 标签发布流程

### 8.1 触发与版本约定

- 新增独立的 Release 工作流，监听发行标签推送；不替换现有 master / PR CI。
- 建议只消费 `v1.0.0` 这类正式版本标签。触发后仍要严格校验标签格式，不能只依赖宽泛的 `v*` 匹配。
- 建议标签指向已经合入 master 的提交，发布流水线验证这一约定。
- 构建必须检出标签对应的精确提交，不把构建内容替换成执行时最新的 master。
- 普通分支推送不发布 Release；不自动创建版本标签。

### 8.2 发布顺序

1. 校验发行标签与目标提交，解析统一版本。
2. 在构建工作区注入桌面与服务端的统一版本，安装锁定依赖，生成开源组件与许可资料，并读取本次详细更新记录。
3. 完成发布所需检查，至少保留现有前端类型检查、测试、构建、同步服务测试、桌面 Clippy 与 Rust 测试的验证标准；标签触发不能绕过现有质量门槛。
4. 分别构建 Mac ARM64、Mac Intel、Windows x64 的 Release 安装包和更新产物，以及 Cloudflare、VPS 两种已编译服务端部署包。Mac 使用 ad-hoc 签名，桌面更新产物使用 Tauri 更新签名。
5. 归集三个桌面平台及两种服务端产物，校验版本、架构、最终名称、签名文件及部署必需文件是否齐全；验证从解压后的服务端发行包部署，而非只验证源码目录。
6. 由统一发布步骤生成包含三个目标的更新清单，并核对所有下载地址。
7. 将全部产物及本次详细更新记录上传到同一个 GitHub Release；可先创建草稿，全部产物齐全且检查成功后再自动公开发布，不能只依赖 GitHub 自动生成的提交列表作为更新记录。

任一桌面平台或服务端包失败时，不把不完整版本公开为新的正式版本，不覆盖当前可用的正式更新入口。同标签重跑应能继续处理未完成的草稿；已公开的正式版本默认不覆盖，修复发行使用新版本标签。

建议优先复用官方 [tauri-apps/tauri-action](https://github.com/tauri-apps/tauri-action) 的构建与 Release 集成能力。三个任务的更新清单必须由统一步骤汇总，避免并发上传互相覆盖；命名适配以最终平台标签为准。

### 8.3 发布凭据与环境

| 配置 | 用途与要求 |
| --- | --- |
| GitHub 发布权限 | 仅发布任务需要仓库 Release 写权限；普通检查保持现有最小权限 |
| Tauri 更新签名私钥 | 所有正式更新包使用稳定密钥签名；公钥写入应用；私钥不提交、不进入安装包或日志 |
| 更新签名私钥密码 | 私钥有密码时通过 Secrets 提供 |
| macOS 签名 | 使用无需账户的 ad-hoc 签名；不要求 Apple 账户、开发者证书或公证 Secrets |
| Windows 代码签名凭据 | 是否在首版配置待确认；不与必需的 Tauri 更新签名混为一谈 |

实现前检查三个桌面目标的 runner、编译工具链和打包工具是否支持当前依赖；不能因同为 `macos-latest` 就假定同时完成了 Intel 和 ARM64 两种架构的构建与运行验证。生成服务端部署包不需要访问用户的 Cloudflare 账号或 VPS；真实环境的连接信息由部署者自行提供。

### 8.4 详细更新记录

- 每个正式 Release 都必须提供面向使用者的中文更新记录，说明本次具体变化和实际影响，不能仅写“修复若干问题”“性能优化”或“请下载附件”。
- 记录基于上一正式发行版本到当前标签之间的实际变更。首发介绍当前已交付能力；尚未实现的需求不得写成已发布功能。
- 按实际变化组织新增功能、问题修复、体验与性能改进、同步服务端变化；有配置变化、数据迁移或兼容限制时，明确写出升级方式及客户端与服务端是否需要同时升级。
- 同时说明三个桌面平台和两个服务端包的用途，提供安装与部署指引。Mac 明确无 Apple 公证及首次打开方式；存在已知限制时如实列出，不为凑栏目虚构更新内容。
- 建议以 `docs/releases/<tag>.md` 保存经过评审的版本更新记录，并在推送对应标签前提交；发布工作流将该文件正文完整写入 Release，附加根据最终产物生成的下载说明。
- 更新记录缺失、为空或仍含未填写占位内容时，发布步骤失败，不公开只有附件的正式 Release。GitHub 自动生成的 PR / 提交列表可以作为附录，不能替代详细正文。
- 应用关于页的发布说明入口指向同一份 Release 记录；更新清单中的说明与 Release 保持一致，避免维护互相矛盾的两套更新文案。

## 9. 验收条件

| 场景 | 预期结果 |
| --- | --- |
| 打开关于 | 独立内容页中只展示关于信息，不混入现有设置表单 |
| 切回设置 | 原有未提交输入与滚动位置保留，搜索和导航正常 |
| 从发行标签构建 | 三个平台中的当前版本、安装包版本和发行版本一致 |
| 离线打开关于 | 当前版本和开源组件清单仍可查看 |
| 检查到相同或较旧版本 | 不提示升级、不降级 |
| 检查到新正式版本 | 只选择匹配当前应用平台和架构的更新包 |
| 检查或下载失败 | 显示失败并可重试，不伪装为最新版本或安装就绪 |
| 下载期间离开关于页 | 下载状态仍保留，返回后可继续查看 |
| 下载完成但暂不安装 | 应用继续正常工作，稍后可主动安装 |
| 校验失败 | 不进入安装，不退出当前应用 |
| 文稿或画布保存失败 | 不交接安装、不丢失内容，应用仍可操作 |
| 默认关闭到托盘开启 | 点击安装仍进入真正的更新退出流程 |
| Windows 更新 | 旧进程结束后安装器完成替换，启动应用显示新版本 |
| NSIS 新装、升级和卸载 | 向导为简体中文，安装器、卸载器及应用快捷方式使用项目自己的图标 |
| Mac 更新 | 两种架构分别通过已确认的安装与重启流程，启动应用显示新版本 |
| Mac 无账户构建 | 不配置 Apple 账户或开发者证书仍能生成两个架构的 ad-hoc 签名产物；首次打开指引与真实结果一致 |
| 安装后数据 | 文稿、素材、偏好和凭据按既有升级规则继续可用 |
| 开源组件多版本 | 每个实际分发版本可查，不用版本范围替代解析版本 |
| 推送合法发行标签 | 自动产出三个桌面平台文件、两种已编译同步服务端包和完整桌面更新清单，发布同一个 Release |
| Cloudflare 部署包 | 解压后使用包内编译入口、配置模板和迁移文件完成部署验证，无需源码或 TypeScript 编译 |
| VPS 部署包 | 解压后按包内说明启动 Node.js 服务或构建容器并通过健康与协议检查，无需再次编译 TypeScript |
| 服务端升级 | 原 D1、R2 或 VPS 持久化卷继续使用，原有设备和同步数据保留 |
| Release 更新记录 | 详细中文记录对应本次实际变化，包含必要的服务端升级说明、下载用途及 Mac 安装指引；缺失记录时不公开发布 |
| 构建失败或产物缺失 | 不公开不完整的正式版本，已发布版本仍可供下载与更新 |
| 自定义产物名称 | 附件名称符合约定，更新清单引用的文件均真实存在且签名可验证 |

自动化测试覆盖版本注入、版本比较、平台匹配、更新状态、退出交接、组件清单生成、详细更新记录及发行产物完整性。服务端以发行包进行 Worker 本地运行或部署校验、VPS 容器启动及同一套 HTTP 契约验证。真实桌面安装及跨版本升级需要在三个目标环境分别验收，并与 CI 构建通过的结果分别记录。

## 10. 建议开发顺序

1. 关于页独立导航和本机版本展示。
2. 构建期版本注入、开源组件清单与许可资源。
3. 手动检查更新、下载进度及本次会话的下载就绪状态。
4. 复用保存退出生命周期，接入 Windows 安装交接与已确认的 Mac 更新方式。
5. 两种已编译同步服务端部署包，以及各自的新装、迁移和升级说明。
6. 标签发行 Actions、三平台桌面打包、中文 NSIS 与应用图标、无账户 Mac 签名、产物命名、更新清单和详细更新记录。
7. 使用两个连续测试版本完成桌面下载、安装、重启和数据保留验收，以及服务端发行包部署和升级验收，再进行正式发行。
