# Milkdown 长文性能改造与验收记录

## 实现

- 正文事务发送本地修订号。自动保存、预览、导出、复制和 AI 全文引用在各自读取边界取得当前 Markdown。编辑器按文档对象复用同一修订的快照。
- 自动保存仍以 750 ms 防抖，连续编辑到 4 秒提交一次。自动写入期间收到的编辑进入下一保存窗口。失焦、关页、退出等显式保存可接管在途任务并等待最新修订落盘。
- 普通块内编辑映射既有装饰并跳过正文布局整理。受影响的复杂块局部重算，结构变化、全局代码行号和链接脚注重新编号按需进行全量更新。查找面板按文档和查询计算匹配，每次最多绘制 200 处高亮。
- AI 选区和章节读取对应片段，全文请求取得当前快照。提案依旧提交局部 ProseMirror 事务，撤销通过文档结构与对应保存修订确认。

## 测量口径

使用 Windows 11 Pro 10.0.26200、Intel Core i9-13900KF、64 GB 内存、WebView2 157 和原生 Tauri Release 构建。窗口为 1360 × 840 CSS 像素，系统缩放 150%。独立应用标识和 SQLite 工作区只加载固定种子的生成文稿。一次性测量脚本、样本生成器及编辑器计时入口已在临时代码清理时移除，本文保留历史测量口径和结果，实际性能优化继续保留。

每组对照各跑 5 轮。每轮重放 200 次插入、100 次光标移动、10 次本地 AI 替换及撤销、30 次段落删除和 10 次粘贴。输入时延从合成事务测到下一次 `requestAnimationFrame`，单位为 ms。打开时延从 Milkdown 初始化测到编辑器句柄可用，第一轮绕开缓存。AI 提交时延覆盖目标校验、片段解析和事务执行。保存 IPC 计时含跨进程调用和 SQLite 写入；图片引用同步使用该合计口径。Long Task 是各阶段观察到的最长单个任务，`—` 表示该轮组中没有浏览器上报的 Long Task。

## 验收结论

- 改造后的 35 轮中，7,000 次输入事务直接触发的全文序列化为 0 次。输入窗口内剩余的快照来自保存。30 万字第 5 轮有 62 次快照与 61 次已完成的保存，该轮输入到下一帧 P95 为 48.8 ms，其余四轮各有 1 次快照。
- 10 万字普通文稿与 5,000 短段落的输入 P95 分别为 16.9 和 20.7 ms，30 万字为 19.0 ms。L6 的 1、20、200 段 AI 改写本地校验与提交 P95 分别为 3.5、6.4、30.6 ms。
- 5,000 短段落和重型节点的打开耗时高于基线，均在 2 秒目标内。5,000 短段落的最后一次全文快照均值为 155.5 ms，百万字为 171.6 ms。两组在整轮操作中仍观测到超过 200 ms 的单个主线程任务。
- 独立工作台中，全选复制、排版预览和 AI 全文上下文都取得了尚未保存的正文。连续 50 次保存、关闭、重开后，SQLite 每次版本递增且正文一致。创建的 50 个 Mermaid 对象 URL 在对应标签关闭后均已撤销，最终编辑器实例数为 0。
- 多标签数据是关闭前和显式 GC 后的采样。5 篇长文切换 P95 为 67.0 ms，关闭后 DOM 元素从 3,582 个回到 728 个。依据 30 万字输入和多标签实测，本次在现有编辑器生命周期内交付。Windows 系统中文输入法的人工键入和其它平台的时延对照留待桌面验收。

`pnpm typecheck`、80 项前端测试、91 项 Rust 测试与 Windows Tauri Release 构建通过。真实 R2 测试按项目配置跳过。默认 Web 构建通过诊断入口隔离检查。
