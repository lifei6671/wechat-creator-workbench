# 中文搜索与相关性排序技术方案

日期：2026-11-23

状态：词级搜索与后台异步重建实现、行为回归已完成；约 50 查询的人工质量标注和完整跨平台验收待完成。重建期间继续编辑保存和字面搜索，追平变更后原子切换索引。验证口径见第 11 节。

## 1. 目标与范围

在现有 SQLite 本地搜索上增加 `jieba-rs` 词级索引和 BM25 排序，改善中文短词、未手动分隔的多个词及结果相关性，同时保留原句、局部字符串、字段限定和原文定位能力。

本期覆盖桌面全局搜索及 MCP `search_entries(mode=workspace)`，不改变 MCP 默认 `keyword` 模式和 `Filter.query` 的字面查询契约。不增加向量数据库、模型调用、同义词服务、拼写纠错或用户词典管理界面。专题私有文本卡片不并入文章搜索。

验收分为两部分：匹配契约通过自动化测试验证；排序效果通过人工标注查询集对比。不能以“接入分词”或“测试通过”代替搜索质量结论。

关联文档：[MVP 技术方案](./mvp-technical-design.md)、[实施计划与验收](./implementation-plan.md)、[MCP 技术访问罗盘](./mcp-access-compass.md)、[界面设计规范](./ui-design-guidelines.md)。

## 3. 选型与架构

### 3.1 复用选择

采用 [messense/jieba-rs](https://github.com/messense/jieba-rs)，复用 Rust 分词实现和内嵌词典，不增加 Python、外部进程或独立服务。项目提供普通分词、搜索模式和自定义词典能力，采用 MIT 许可证；接入时保留许可声明并更新项目第三方依赖记录。

排序直接使用 SQLite FTS5 自带的 `bm25()`，不引入独立搜索引擎。FTS5 支持列权重、词频和文档长度因素，适合现有 SQLite 数据模型。[SQLite BM25 文档](https://www.sqlite.org/fts5.html#the_bm25_function)

已接入 `jieba-rs 0.11.0` 并更新 `Cargo.lock`，与项目 Rust 工具链完成编译和测试。仅使用内嵌词典，不启用 TF-IDF、TextRank 等附加功能；第三方许可已进入现有许可证生成流程并登记在 `NOTICE.md`。

### 3.2 两种索引的职责

```text
entries.title / entries.content_md
    ├── 现有触发器 → entries_fts（trigram，字面子串）
    └── 词级触发器 → Rust 分词函数 → 活动词级槽（BM25）
                     └── 构建期间记录 dirty revision
后台独立连接 → 分批扫描与分词 → 备用词级槽 → 追平 dirty → 事务切换活动槽
词级双槽：entries_words_fts / entries_words_alt_fts（ascii）
状态与变更：search_index_state / search_index_dirty

桌面查询 / MCP workspace
    → 既有语法解析
    → 字面候选与词级候选
    → 分类、标签、状态、可见性等过滤
    → 去重、全量相关性排序
    → 条目分页
    → 原文匹配行、高亮与定位
```

索引均是本地派生数据，`entries` 继续作为内容来源。词级索引不进入远程同步实体或变更日志；数据库整库备份自然包含索引及内部版本记录。

## 4. 分词与查询契约

### 4.1 分词规则

1. 文档和查询共用一个 Rust 分词与规范化实现，复用进程内初始化的 `Jieba`，不逐条内容创建词典。
2. 首期采用普通精确模式 `cut`，HMM 固定启用。搜索模式 `cut_for_search` 会输出重叠子词，不直接把这些子词平铺为文档词频或全部转换为查询 AND 条件，避免重复评分和额外限制。是否增加子词扩展由评测决定，不作为本期默认行为。
3. 使用一致的 Unicode 小写规则，保留重音差别；不做繁简转换、同义替换或拼写改写。
4. 过滤纯空白、纯标点词元，保留有意义的一字词、数字及英文内容。索引保留实际词频，查询中的重复词只生成一次匹配条件。
5. 在原始 Markdown 上逐行调用 jieba，索引、查询和高亮共用返回“规范化词元 + 原文字节范围”的函数。分词后统一 Unicode 小写、拆开 ASCII 非字母数字分隔符，保留有意义的非 ASCII 内容，以空格连接词元。FTS5 使用 `ascii` tokenizer：Unicode 小写由 Rust 完成，非 ASCII 词元由 jieba 确定，避免 `unicode61` 再次改变词元边界或重音规则。查询与索引使用相同函数，不独立实现第二套分隔规则。
6. 首期仍从原始 Markdown 分词，保留代码、链接及现有可搜索内容；不同时引入正文提纯与偏移映射系统。链接地址等内容仍可能影响评分，纳入评测样本并在报告中单独观察。

内嵌词典、分词器版本、HMM、规范化和 FTS tokenizer 参数共同组成内部索引签名。任一变化都要求重建词级索引，不能让新查询规则直接读取旧词典生成的索引。Cargo.toml 精确固定 `jieba-rs = "=0.11.0"`，避免普通 `cargo update` 在不改变签名时自动更新词典；主动升级分词器或修改词典、规范化规则时，必须同步更新 `search_index.rs::SIGNATURE`，并验证旧签名触发后台重建。

### 4.2 匹配规则

| 查询 | 本期语义 |
| --- | --- |
| 未加引号的普通文本 | 每个既有 Text 子句满足“原文包含该文本，或该子句的有效分词全部在标题及正文中命中”；多个子句仍为 AND |
| `公众号排版技巧` | 保留整串字面命中；若分成多个有效词，也允许这些词分布在标题、正文的不同位置，不保证具体分词结果 |
| `公众号 排版` | 两个子句都必须满足；不改为任意一个词命中即可 |
| `"公众号排版"` | 连续原文短语，保持字面语义，不经分词扩大结果 |
| `file:`、`path:`、`tag:`、`content:` | 保持当前字段范围、包含语义及分组关系；本期不扩大为词级查询 |
| `line:(...)`、`section:(...)` | 保持字面匹配，分别要求同一行、同一 Markdown 章节内满足全部词，不做词级扩展 |
| `[状态:...]`、`[摘要:...]`、`[来源:...]` | 保持当前属性解析和匹配语义 |
| 区分大小写开启 | 使用现有大小写敏感字面匹配，不使用已小写化的词级索引扩大结果 |
| 只有标点或分词后没有有效词元 | 仅执行既有字面分支，不生成空 MATCH 表达式 |

解析结果需要保留“是否加引号”的信息；当前 `Clause.terms` 会移除引号，不能在移除后猜测用户意图。内部解析结构可扩展，返回给桌面与 MCP 的现有 `clauses` 结构保持兼容。

先解析字段、引号和分组，再对符合条件的 Text 值分词。用户输入不直接作为 FTS 运算符；词元按 FTS 字符串规则引用、转义，并使用 SQL 参数绑定。`OR` 是普通字面词，现有查询没有用户可输入的 OR 运算符。冒号、括号仅用于既有字段和分组语法，不获得额外的 FTS 执行语义。

词级分支必须与字面分支在查询时合并；不能只在字面结果为空时才查询词索引，否则不同分页和不同条目会获得不一致的匹配规则。纯一字查询仍可能很宽泛，不承诺分词能消除这种歧义。

### 4.3 字段和标签边界

普通搜索的召回范围仍为标题、正文。只有标签包含查询词而标题和正文均不匹配的条目，不因此进入普通结果；用户可使用 `tag:` 查标签。

在已召回候选内，可以用标签名与普通查询词的完整匹配作为排序信号；复用现有 `entry_tags`、`tags`，不把标签拼入正文词频，不新增标签索引同步流程。摘要、来源、路径仍仅在相应限定查询中参与匹配。

## 5. 数据模型与索引维护

### 5.1 词级 FTS 表与构建元数据

通过 `0031_word_search.sql` 新增普通、带内容的 FTS5 表：

```sql
CREATE VIRTUAL TABLE entries_words_fts USING fts5(
    title_words,
    body_words,
    tokenize='ascii'
);
```

`rowid` 对应 `entries.rowid`。表内保存分词文本，不直接将 `entries` 设为 external content：原始标题、正文不是索引所需的分词文本。普通 FTS 表可直接更新和删除，首期不增加另一张投影表或 contentless 特殊维护逻辑。

`0032_background_word_search.sql` 增加相同 schema 的 `entries_words_alt_fts`。两个固定槽分别对应 `active_slot=0/1`；触发器只更新活动槽，后台只构建备用槽，不动态改表名。切换后保留旧槽，下一次构建开始时重置备用槽。两份词级文本与 FTS 数据增加磁盘占用，需连同 WAL 峰值单独测量。磁盘预算按常驻两份词级索引估算，另计原始 entries、trigram 索引与 WAL；该开销持续到下次备用槽重置。两个固定表仍被触发器引用并参与备份 schema 校验，切换后不直接 DROP 旧表。

| 内部表 | 字段与含义 |
| --- | --- |
| `search_index_state` | 单行 `id=1`；`active_slot`、当前活动槽的 `signature`、成功切换次数 `generation`、是否处于构建周期的 `building` |
| `search_index_dirty` | `entry_rowid` 主键和该待处理条目的 `revision`；同一条目变化合并，revision 递增 |

迁移从旧 `app_settings['search.word_index_signature']` 转移签名到状态表并删除旧键。签名匹配当前实现才允许词级查询；`building` 仅表示构建周期，不能单独作为“可搜索”或“线程仍存活”的依据。后台故障单独通过工作区 Worker 报告。

软删除内容保留索引，由查询层隔离正常库与回收站；已清除内容不保留词级文档。BM25 的语料统计包含仍保留的软删除内容，首期不为正常库和回收站分别维护索引。

### 5.2 增量更新

新增纯函数 `workspace_search_tokens(text)`，在数据库触发器中调用。触发器覆盖：

| 事件 | 索引操作 |
| --- | --- |
| INSERT 未清除条目 | 使用新 rowid 和分词后的标题、正文写入 |
| 标题或正文实际变化 | 在同一事务中更新对应词级文档 |
| 清除条目 | 删除对应词级文档，即使业务采用保留空壳记录的方式清除 |
| 物理 DELETE | 删除对应词级文档 |
| 仅状态、分类、标签、时间等变化 | 不重新分词；过滤与标签加分实时读取关系表 |

新词级触发器明确声明 `AFTER UPDATE OF title, content_md, purged_at ON entries`；仅在标题、正文或清除标记实际变化时执行。删除旧词级文档，再仅为 `new.purged_at IS NULL` 的记录插入新文档，覆盖正文变化与清除两个路径。当前业务清除会同时置空标题、正文；新增索引仍须独立响应只更新 `purged_at` 的状态变化，不能仅在 WHEN 中检查却遗漏监听列。正常 INSERT、UPDATE 与清除路径的触发器需成套测试，避免重复插入相同 rowid。

将函数和词元处理放入内部模块 `src-tauri/src/search_index.rs`，由数据库初始化及内容搜索共用。通过 `db.rs::apply_migrations` 的统一入口注册函数；即使数据库已是当前版本、没有迁移 SQL，该入口也执行注册。工作区打开、迁移测试、备份校验的正式与预览参考数据库均经此入口，不靠调用方各自记忆注册。只读快照检查不为读取内容执行分词，也不引入进程级 `sqlite3_auto_extension`。

现有 `SEARCH_FUNCTION_FLAGS` 含 `SQLITE_DIRECTONLY`，不能直接复用到触发器函数。新函数只依赖输入与进程内固定词典，使用适合纯函数的 UTF-8、DETERMINISTIC、INNOCUOUS 标志，不设置 DIRECTONLY；现有查询辅助函数保留原标志。[SQLite 函数标志](https://www.sqlite.org/c3ref/c_deterministic.html)

触发器在同一内容事务中读取 `active_slot`，更新唯一活动槽。构建期间（`building=1`），INSERT、正文/标题/清除标记实变和 DELETE 同时向 dirty 表 UPSERT rowid 并递增 revision；删除条目的 rowid 也保留在队列中，不依赖外键或条目仍存在。软删除与恢复不改变词元，实时过滤继续生效。后台独立连接同样显式注册分词函数。

触发器使编辑保存、MCP 修改、公众号/GitHub 导入、同步应用及合并更新共用同一索引维护边界。分词或 SQL 更新失败时回滚内容事务并沿已有错误机制返回，不提交正文后再忽略索引失败。普通 SQLite 工具如果未注册该函数，不能直接修改带这些触发器的内容表；离线维护须使用应用提供的连接初始化流程。

### 5.3 后台构建与追赶协议

工作区初始化仅完成连接、迁移、元数据检查和既有完整性检查，不在启动线程全量分词。无未清除条目的空库可直接标记当前签名。实际桌面工作区在 setup 中启动单个 Worker，使用同文件的独立 SQLite 连接；普通 `Workspace::open`（包括备份校验）不自动创建后台线程。签名已匹配时不启动重建。

| 阶段 | 操作与一致性边界 |
| --- | --- |
| 开始 | 短 `BEGIN IMMEDIATE` 内读取活动槽，按正式 schema 重建备用槽，清 dirty，置 `building=1`，记录当前最大 rowid 后提交。此边界之前的数据由基础扫描覆盖，之后的变化由触发器记录 |
| 基础扫描 | 按 rowid 游标、上限及每批 32 条读取未清除 entries，读取后释放语句；在写事务外逐行 jieba 分词；用短事务写备用槽。新增的较大 rowid、删除、清除、已扫描条目再次编辑均由 dirty 补齐 |
| 追赶 | 用一次读取获取 dirty 的 `(rowid, revision)` 与当前正文；未找到或已清除的条目视为删除。事务外分词，再在短事务中覆盖/删除备用文档，仅以相同 rowid **且相同 revision** 删除已处理标记 |
| 切换 | 在 `BEGIN IMMEDIATE` 内重新确认 dirty 为空；不为空就继续追赶。为空时同事务更新 `active_slot`、新签名、`generation+1` 和 `building=0`，提交后才发出既有 `workspace-changed` 事件 |

基础扫描不持有跨批次的全库快照；它允许写入旧版本到备用槽，但所有构建期间已提交变更均留在 dirty 中，切换前必须重读当前 entries 覆盖。追赶分词期间又发生编辑时，条件确认不会删除更高 revision 的标记，必须再次处理。物理删除后 rowid 被复用也按此规则处理，不能误用旧正文。

SQLite 只有一个写事务。最终检查与元数据切换持有同一写锁：切换前提交的保存已进入 dirty，切换后提交的保存读取新活动槽并同步维护。因此没有“队列刚排空、保存晚到、切换漏写”的窗口，也不需要暂停编辑器或先提交正文再异步更新活动索引。后台不持有工作区 Mutex，分词在写锁之外，批次间主动让出执行；写锁等待沿用项目 2 秒 busy timeout，失败明确上报，不无限重试。[SQLite WAL](https://www.sqlite.org/wal.html)、[事务与 BEGIN IMMEDIATE](https://www.sqlite.org/lang_transaction.html)

后台异步只移除全库分词对启动的阻塞，不消除既有迁移、完整性检查与 SQLite 短写锁等待。普通保存仍同步维护字面索引与活动词级索引，失败回滚保存事务。持续大量写入时可以延后就绪，不能跳过 dirty 以保证限时完成。

### 5.4 查询可用性与代次

签名不匹配时禁用词级候选、BM25 和词级高亮，继续执行原有字面搜索和过滤；不查询半成品或用新分词规则读取旧签名索引。正文保存、新增、导入与同步正常进行。重建完成后，新请求使用新活动槽。

每次工作区查询在一个 SQLite 读事务内读取状态、选槽、计算总数/排序/分页，并读取该快照的正文与版本；随后以已读取的原文生成高亮，保证单次响应来自同一快照。读事务跨越切换时仍返回旧快照的一致结果，不能中途改读新槽。

响应增加 `search.indexGeneration` 与 `searchMatches.indexGeneration`，格式为 `generation:literal` 或 `generation:words`。条目版本只表示正文变化，不能识别索引代次。前端在条目续页和匹配行续页返回代次不同时丢弃该页并重取首页；代次变化也重建匹配行本地状态。此机制覆盖切换事件与在途分页交错，不将旧字面集合与新词级集合拼接。MCP workspace 返回同一代次元数据；调用方跨请求分页应在代次变化后从第一页重新读取。普通内容编辑的版本/刷新契约继续沿用。

### 5.5 中断、退出、备份与恢复

重建不修改正文、条目版本、更新时间、历史记录或远程同步状态。后台出错保留活动槽和旧签名，通过工作区事件刷新搜索错误状态；仍可字面搜索与保存。错误不伪装为索引就绪，也不把部分备用槽直接提升。下次启动或取消退出后重启 Worker，重新清备用槽并从当前 entries 构建，放弃上次半成品，不依赖内存游标恢复。

准备退出、安装更新、恢复切库均先取消并 join Worker，再执行既有 checkpoint/关闭/替换文件流程；分词按条目检查取消，SQL 按批提交。取消退出时恢复后台构建。恢复关闭成功后移除旧 Worker，不能让旧路径回调或后台连接继续接触已替换的数据库。

数据库单文件备份包含两个槽和状态/dirty；构建中取得的快照允许含备用半成品，活动签名仍未更新。恢复后走正常迁移和签名检查，再后台重新构建。两槽始终采用正式迁移定义的固定 schema，参考库与备份的严格 schema 校验保持有效，不增加动态表或放宽校验。

## 6. 候选合并与排序

### 6.1 查询执行

0. 在同一读事务中固定活动索引与代次；词级未就绪时按 §5.4 仅执行字面分支。
1. 为每个可分词的 Text 子句构建“字面命中 OR 全部分词命中”的候选条件；词级 AND 允许跨标题和正文满足。
2. 合并同一条目的多路命中，关联 entries 后执行所有原有筛选。删除状态、清除状态、分类、标签、类型与导入筛选必须在条目分页前生效。
3. 对查询中普通文本的有效词元构建统一、去重的评分查询，计算词级候选的 BM25；评分查询可使用词元 OR，是否有资格返回仍由第 1、2 步决定，不能用评分查询替代匹配条件。
4. 在合法 FTS MATCH 上下文内计算 `bm25(active_table, title_weight, body_weight)`（表名只能来自两个内部槽常量），再将 rowid 和分数作为普通结果关联。实现时检查 CTE/子查询的执行计划与物化方式，不能在不支持的聚合或窗口上下文直接调用 BM25。
5. 总数、排序及去重完成后再应用 LIMIT/OFFSET。不分别截取两路前 N 条后拼接，也不先分页再在前端评分。

### 6.2 相关性顺序

采用清楚的分层排序，不将 trigram 与词级 BM25 的原始分数混加：

1. 标题与 Text 或 `file:` 子句提供的完整标题查询文本相等的条目优先；只包含 path/tag/属性等非标题限定时不使用该层。`file:` 保留既有标题完全匹配优先的排序行为，但其候选范围仍按字面匹配。
2. 所有普通 Text 子句均可按原文直接命中的条目，优先于仅通过分词扩大召回的条目。
3. 在同层中，按标题完整词命中数量、标签名与查询词完整匹配数量降序比较。标题完整词以分词后的词元判断，避免只按子串计数。
4. 再按词级 BM25 从小到大比较；只有字面命中而没有词级分数的条目，在前述同层同信号条件下排在有词级分数的条目之后。
5. 最后沿用标题 `COLLATE NOCASE`、条目 ID 的稳定并列规则。

标题与正文的 BM25 初始权重为 `5:1`，仅作为待评测的实现起点，不代表已证明最优。评分不再使用“命中行数”，不为正文越长或换行越多额外加分。纯字段查询或大小写敏感查询没有可用词级分数时，使用适用的标题信号及稳定排序，不为了评分改变匹配集合。

字面短词为常用汉字区间 U+4E00–U+9FFF 与 ASCII 数字组成时，直接使用 SQLite `instr`，无需对整篇正文执行 Unicode 小写转换；字面排序信号采用相同条件省略大小写折叠。其他输入仍使用既有 Unicode 小写规则，尤其不能把“字符本身没有大小写”误当成安全条件：组合点号 U+0307 可以出现在 `İ` 的小写展开中，须保留原有匹配与范围换算。

未命中评分查询的字面候选表示“没有词级评分记录”，以 NULL/缺失状态与有效 BM25 分数区分，不将其伪装成分数 0。补充“相同字面命中但分词覆盖不同”的排序样本；评分侧 `cut_for_search` 扩展与匹配侧扩展分别评测。只扩展评分查询并不保证文档索引具有对应子词，本期不默认启用，也不因此改变普通分词的词频统计。

名称、更新时间、创建时间等用户指定排序保持原定义；置顶列表的专用排序优先级不改变。默认值仅作用于没有保存排序偏好的用户，不覆盖既有 `workspace-search-sort` 值。

## 7. 原文片段、定位与接口

词级索引中的空格和 token 位置不是 Markdown 原文偏移，不能把词表的 `highlight()` 或 `snippet()` 结果直接交给编辑器定位。

在现有 `collect_matches` 中扩展命中判定：字面分支继续寻找原词、原句；词级分支复用 §4.1 的逐行函数，并直接使用词元原始字节范围，随后换算 UTF-16 偏移。索引与高亮不得分别按整篇和逐行采用不同的预处理规则，也不得在小写化后的字符串上取得偏移后直接用于原文。正文的 LF/CRLF 与原始字节偏移保持一致。

词级分支只高亮实际命中的完整词元；字面分支仍允许合法的子串高亮。例如扩展查询中的 `layout` 不应点亮只有 `layoutExtra` 的词元，但用户明确字面搜索 `layout` 时，其在 `layoutExtra` 中的原文出现仍是合法命中。首期查询时重用纯分词函数，不持久化 token→offset 映射；只有测量表明查询期分词是主要瓶颈时，再评估增加映射及其事务维护成本。

多个词可以跨行、跨标题和正文满足一个普通 Text 子句，因此不能要求每条片段包含全部词。返回实际含命中词的正文行；只在标题命中的条目允许没有正文匹配行。引号、line 和 section 的片段继续服从各自的字面或作用域约束，不混用词级扩展。

`searchMatches.version` 继续验证正文版本；新增索引代次与分页重置契约见 §5.4。行号、UTF-16 `start/ranges`、上下文、片段展开及匹配行分页继续沿用现有结构。`matchPage` 应保留同一查询计划与匹配集合；条目分页总数仍按去重条目统计，匹配行总数仍按实际命中行统计。

桌面和 MCP workspace 共用同一后端，不各自实现分词或排序。MCP keyword 的整串字面查询、已有参数及分页保持兼容。

本次复用现有元素：搜索框供输入；大小写按钮选择字面匹配；排序控件选择顺序；命中片段核对原文。搜索摘要原计数位置在索引未就绪时复用既有“正在载入…”并设 `aria-busy`，字面结果仍可浏览；成功后恢复计数。后台错误在同一固定区域显示错误，保留完整 title 和可访问性告警，不新增控件、帮助段落或 Toast。续页跨代次时在既有错误区域反馈并刷新。

### 9.2 检索质量

准备约 50 个固定查询，覆盖已知标题、中文短词、多个关键词、连续中文、原句、专有名词、字段筛选及无结果输入。另列同义改写、错别字和自然语言问题用于记录能力边界，不将本期不支持的语义能力计作已实现。

在相同数据快照上保存旧实现与新实现结果，从两者前 20 条的并集中人工标注不相关、相关、高度相关。记录前 5 条和前 10 条排名及以下指标：

- `Hit@5`：前 5 条是否出现至少一条相关结果。
- `MRR@10`：前 10 条中首条相关结果名次的倒数，没有则为 0。
- `nDCG@10`：考虑相关等级与名次的排序质量，理想序来自同一标注候选池。
- `P@5`：前 5 条相关结果数除以 5；不足 5 条的空位不算相关。

该候选池不能证明全库召回率，不报告未经完整标注的 Recall。验收要求：原句、字段和 keyword 契约无回归；已知完整标题排首位；整体 nDCG@10、MRR@10 不低于基线，中文短词与连续中文查询组应有可解释的改善。逐条审查退化查询，不能仅报告平均分。

### 9.3 性能与平台

沿用 MVP 的 1000 篇约 5000 字文章及 5 万字长文样本，另测 10000 篇规模，固定覆盖两字短词 `排版`、单字 `公`、纯字段 `file:公众号研究`、常见词多子句及无结果输入。必须包含“连续字面串稀少，但按目标词典分词后，各常见词在大量文档中同时出现”的扩大召回样本，例如固定词典下的 `公众号排版` 与正文中分散出现的词。`中国 发展` 已是既有多子句 AND 查询，不能单独用它证明新实现扩大了召回。

固定机器、数据、构建模式、SQLite/jieba 版本；分别记录冷查询、预热后查询、首次构建、普通启动、保存增量分词耗时和数据库体积。合成基准的字面路计数使用与正式查询相同的解析与字段条件；纯字段查询无词级扩展，词级计数记为 0，不按标题或正文的无范围包含匹配冒充字段候选。报告每个查询的字面候选数、词级候选数、重叠数及最终过滤后条目数，区分算法开销与有意扩大的结果集。每组预热后重复查询，报告 p50/p95，不能以单次耗时作结论。

初始验收目标为 1000 篇样本上的常规词级及扩大召回查询预热后 p95 不超过 150ms；与基线匹配集合相近的兼容查询，p95 不退化超过 20%。扩大召回查询不直接套用与旧字面查询的 20% 比例，而检查绝对耗时及各路候选规模。10000 篇样本单独报告扩展趋势和重建耗时。这些是优化构建下待实测的项目目标，不是已有性能数据；Debug 测量只用于定位瓶颈。分词在保存路径的实际开销必须随报告给出；后台构建单独报告启动调度耗时、总耗时、构建期间真实保存次数及 p50/p95/最大耗时、切换后最新保存可检索性，并与无重建保存基线比较。两槽与 WAL 峰值空间单列，不用总重建耗时冒充前台阻塞；若超标，先依据执行计划和测量定位，再调整实现，不能通过删掉困难用例掩盖问题。

共享 Rust、SQLite 与前端逻辑均需评估 Windows、macOS。两端分别检查词典打包、启动、中文输入法、搜索高亮跳转和恢复后重建；自动化通过不等于原生窗口实测。实施后的交付明确列出各平台已执行检查及未验证项。

验证命令以实施时仓库脚本与 CI 为准：相关 Rust 搜索/迁移/恢复测试优先，后续执行项目要求的 Rust 与 TypeScript 检查及受影响前端测试。
