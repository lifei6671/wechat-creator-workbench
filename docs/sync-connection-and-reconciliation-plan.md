## 1. 目标与用户行为

用户连接自己的同步服务时，只填写服务地址、连接密钥和设备名称。应用验证权限后，根据本地同步记录与云端状态，自动完成初始化、下载、合并和增量同步。

“重新安装后的空工作区”指原电脑曾经连接过，卸载后重新安装，当前安装已经没有原业务数据库或同步记录。它代表尚未获得云端副本。应用内主动删除文章，继续通过明确的删除记录同步。

| 使用场景 | 目标行为 |
| --- | --- |
| 新部署服务，本地已有内容 | 自动登记设备并上传本地内容，完成云端初始化 |
| 新部署服务，本地也为空 | 完成空工作区初始化，后续正常同步 |
| 重新安装后本地为空，云端已有内容 | 使用同一份连接信息登记当前安装，自动下载云端内容 |
| 新设备已有本地内容，云端也有内容 | 获取云端快照，自动合并，并继续上传本地独有内容 |
| 已连接设备正常打开应用 | 复用有效设备凭据，按已有版本和进度同步 |
| 本地数据库保留、设备凭据丢失 | 重新授权，保留本地修改及同步历史，核对在途操作后继续同步 |
| 窗口失焦、最小化或收起到托盘 | 应用进程继续交换已保存的数据，编辑器在安全时机应用远端变化 |
| 窗口恢复可见并重新获得焦点 | 刷新本地同步状态，同时请求一次远端检查；下载后按既有条件安全应用 |

实施完成后的主要验收链路：电脑 A 上传内容 → 清除 A 的应用数据并重新安装 → 输入原服务地址与连接密钥 → 自动获得云端内容 → 在 A 修改文章 → 电脑 B 收到修改。

### 1.1 保持的架构

- 每个自托管服务对应一个所有者的写作工作区，设备平等读写。
- 桌面端沿用 Tauri、Rust、SQLite、Milkdown 和现有保存队列；同步单位继续采用业务实体。
- 服务端沿用 Cloudflare Workers + D1 + R2，以及 Node.js + SQLite + 文件存储两种运行方式。
- 继续使用实体稳定 ID、远端修订号、增量游标、删除墓碑、持久化待发送操作和现有冲突处理。
- 文章正文继续作为整体冲突单元；双方修改同一篇文章时，保留两侧内容供处理。
- 完整数据库备份继续用于用户主动选择的工作区恢复；常规连接和同步保持业务数据合并语义。

## 3. 统一连接与密钥规则

### 3.1 用户保存一份连接信息

界面名称统一为“连接密钥”，HTTP 字段沿用 `accessKey`，数据库沿用 `sync_identity.access_hash`。

新部署时继续通过现有 `SETUP_SECRET` 配置一把高强度随机密钥。首次连接成功，将同一把密钥的摘要固化到 `access_hash`。用户随后添加电脑或重新安装时，继续使用这份服务地址与连接密钥。

连接过程保持密钥稳定；“更换连接密钥”是设备管理中的明确操作，复用现有轮换接口。轮换只影响后续设备接入，已授权设备继续使用各自的设备令牌。

应用可将用户输入的连接密钥保存在系统钥匙串中，用于用户主动点击“复制连接信息”。业务 SQLite、数据库备份、错误信息和运行日志中不保存明文密钥。旧安装没有保存明文密钥时，界面允许输入现有密钥，或明确执行“更换连接密钥”。

“复制连接信息”只复制已经保存的值，不隐式调用密钥轮换接口。密钥在其他设备被轮换后，旧副本按服务端校验结果提示更新。

### 3.2 设备身份

- 有效设备令牌存在时，沿用原设备身份。
- 新安装没有原设备令牌时，登记新设备，连接同一个云端工作区。
- 普通连接不依据电脑名称、硬件标识或数据库内的旧设备编号自动接管另一台设备。
- 恢复指定原设备身份继续使用既有恢复密钥与辅助恢复入口。
- 本地设备凭据被拒绝后显示重新授权入口；后台任务不会使用保存在钥匙串中的连接密钥自动重新登记，从而绕过用户的设备撤销操作。

### 3.3 服务端统一接口

在 `GET /v1/meta` 增加：

~~~json
{
  "unifiedConnect": true,
  "operationReceiptLookup": true
}
~~~

继续返回现有协议版本、`claimed`、`seedStatus`、`serverInstanceId` 和 `syncEpoch`，补充 `seedDeviceId`，供首次初始化等待和恢复提示使用。协议版本保持 1，新增能力由标记表达。

新增 `POST /v1/connect`：

~~~json
{
  "accessKey": "<64位十六进制连接密钥>",
  "deviceToken": "<客户端预生成并持久化的设备令牌>",
  "name": "办公电脑"
}
~~~

请求携带预检得到的 `X-Sync-Instance` 与 `X-Sync-Epoch`。登记事务核对二者，避免预检后服务历史发生变化而写入错误绑定。请求不包含本地目录状态或同步方向。

成功统一返回 HTTP 200：

~~~json
{
  "protocolVersion": 1,
  "deviceId": "<设备ID>",
  "serverInstanceId": "<服务实例ID>",
  "syncEpoch": "<同步世代>",
  "seedStatus": "ready",
  "seedDeviceId": "<首次上传设备ID或null>"
}
~~~

连接接口负责授权和返回当前同步身份。上传、快照下载和数据应用仍由既有同步接口执行。

### 3.4 密钥校验与旧服务迁移

| 数据库状态 | 授权依据 | 成功后的处理 |
| --- | --- | --- |
| access_hash 已存在 | 只校验当前 access_hash | 登记设备，保持密钥不变 |
| access_hash 为空、claimed=0 | 校验当前部署的 SETUP_SECRET | 原子设置 access_hash、claimed、claim_device，并登记设备 |
| access_hash 为空、claimed=1 | 校验当前部署的 SETUP_SECRET | 将该密钥固化为 access_hash，登记新设备，保留原认领设备及数据 |
| access_hash 已存在，输入仅匹配旧 SETUP_SECRET | 授权失败 | 保持现有认证状态 |

旧服务的兼容变化必须写入升级说明：**对于已认领且从未设置接入密钥的服务，首次统一连接会把当前部署密钥转为可重复使用的连接密钥。已有接入密钥的服务继续沿用原接入密钥。**

`SETUP_SECRET` 的兼容入口只在 `access_hash IS NULL` 时有效。接入密钥轮换后，即使部署环境仍保留旧 `SETUP_SECRET`，旧值也不能用于新增设备。服务启动过程不覆盖数据库中的接入摘要。

若旧服务既没有接入摘要，也已删除部署环境中的 `SETUP_SECRET`，使用已有授权设备生成连接密钥，或使用既有管理员恢复能力。普通连接不会凭服务地址推断所有权。

### 3.5 事务和连接幂等

在 `auth.ts` 增加 `connect`，复用 `Database.batch` 与现有设备表，按以下步骤在一个事务内完成：

1. 校验预期实例与世代，按当前 access_hash 或一次初始化规则校验连接密钥。
2. 有条件插入设备，以现有 `token_hash` 唯一约束处理相同请求重试。
3. 仅在有效设备已登记且授权条件成立时初始化 access_hash，设置 claimed=1；只有原状态未认领时才设置 claim_device。
4. 读取有效设备、当前接入摘要和同步身份，返回登记结果。

禁止使用事务外读取的 claimed 值直接决定后续无条件写入。两台设备并发首次连接时，共享同一连接密钥即可先后成功；首次数据上传仍由现有 seed 协议原子确定上传设备。

客户端复用现有 `Credential.pending`：

1. 生成设备令牌并先写入钥匙串 pending。
2. 发起连接请求。
3. 响应成功后保存 active 凭据与 SQLite 绑定。
4. 响应丢失时复用原 pending；可先用该令牌调用现有设备查询确认登记结果。
5. SQLite 绑定保存失败后，下一次仍沿用已经持久化的设备令牌完成登记确认。

同一 pending 重试只能得到一个设备登记。已撤销令牌不能通过登记重试被自动恢复。

旧 claim、join、recover 路由继续服务现有客户端，新普通表单统一走 /v1/connect。新客户端遇到缺少 unifiedConnect 能力的旧服务时提示升级，保持本地数据和既有同步记录。

## 4. 客户端自动协商

普通 `sync_connect` 参数收敛为服务地址、设备名称和连接密钥；有效凭据重连允许省略密钥。前端不传 `method` 或 `rebuild`。原设备身份恢复保留单独的辅助命令。

连接与同步共用 `SyncConnection.gate`。握手成功与业务数据同步完成分别反馈。

### 4.1 判定依据

| 本地/云端状态 | 内部动作 |
| --- | --- |
| 无绑定，云端尚未初始化 | 登记设备后参与 seed；获得初始化权的设备上传本地内容 |
| 云端正在由另一设备初始化 | 显示“正在等待云端初始化”，按现有调度节奏检查；ready 后继续 |
| 无本地基线，云端 ready，本地业务内容为空 | 下载并应用完整快照 |
| 无本地基线，云端 ready，本地已有内容 | 下载快照，执行既有首次合并 |
| 同一实例和世代，有有效本地基线 | 继续增量同步 |
| 同一实例和世代，增量进度低于保留水位 | 自动重新下载快照，按第 6 节对账 |
| 凭据失效，但本地保留同步历史 | 等待重新授权；保留历史和待发送操作，按第 5 节核对在途操作 |
| 服务身份、历史一致性或备份来源需要复核 | 保存明确暂停原因，进入第 7 节处理 |

初始化状态以云端 seedStatus 与 seedDeviceId 为准。云端已 ready 时，尚未初始化的客户端先按第 5 节核对旧操作，再进入快照路径，不因本地 seeding 残留继续调用 finish。云端仍在 seeding 且上传设备不是当前设备时，进入等待；需要恢复原上传设备时使用既有指定设备身份恢复入口。

“本地为空”采用现有业务判定，包含文章、素材、专题及内置目录状态。判断优先级为同步历史与操作记录，其次才是业务内容数量。已有删除记录的工作区继续同步删除。

### 4.2 重装后的主路径

新安装无绑定、无同步历史时：

1. 获取服务元数据并完成设备登记。
2. 云端 ready 时执行现有 `download_baseline`。
3. 复用快照起始水位、结束水位与补拉机制，完成一致快照暂存。
4. 通过已有应用入口落库，记录初始化完成和游标。
5. 更新同步状态，正常打开文章并按现有策略获取附件。

保留文章、分类、专题、卡片及素材的稳定 ID。设备 ID 可以重新生成。现有软删除文稿按云端状态进入废纸篓。

### 4.3 非空首次接入

本地尚未建立同步基线且已有业务内容时，在普通连接区域展示：

> 连接后将合并本地与云端内容；同一内容存在不同修改时，会保留双方版本供你处理。

展示条件复用第 4.1 节的本地业务空库判定，所需结果通过现有工作区或连接状态读取链路提供。用户仍通过一个“连接”操作完成授权与后续协商；内容协调继续以同步历史、稳定 ID 和版本为依据。呈现规则见第 9 节。

复用 `merge::baseline` 的归档、目录名称协调、图片标识处理和引用重建：

- 双方独有的文章、专题等内容保留。
- 同名但不同 ID 的文章分别保留，不按标题判重。
- 相同 ID、相同业务内容视为已对齐。
- 相同 ID、不同正文或画布内容进入已有冲突处理。
- 首次合并成功后，由数据库中的可上传记录触发后续交换。

`mergeArchive` 只表示生成了本地恢复副本，供界面打开位置。它不承担控制同步轮次的职责。应用基线后发现可上传内容时，立即唤醒网络任务，用户无需再次点击。

## 5. 在途操作与重新授权

### 5.1 保留原操作身份

当前服务端按 `epoch + device_id + operation_id` 保存回执。新设备 ID 下发送旧 operation_id，不能自动命中原回执。

在 `sync_outbox` 增加一个字段 `origin_device_id`，记录冻结操作创建时的设备 ID。迁移时从原 sync_binding 回填；以后创建 outbox 时同时写入。连接重登记更新 binding 前，旧 outbox 的来源设备必须已经持久化。

原操作中的 operation_id、mutations、baseRevision 和 generations 保持冻结。正常同设备重试继续使用原包。

同一服务世代内重新授权后：

- 保留 cursor、revisions、dirty、inbox、issues 和 outbox。
- 新设备令牌可以更新当前 binding.device_id。
- 旧 outbox 先核对原设备命名空间中的回执，再决定后续处理。
- 服务实例或世代变化不沿用这条普通重登记路径。

### 5.2 独立读取操作回执

新增逻辑只读接口 `POST /v1/sync/receipts/lookup`：

~~~json
{
  "originDeviceId": "<原操作所属设备>",
  "operation": {
    "operationId": "<原操作ID>",
    "mutations": []
  }
}
~~~

上述示例展示请求结构；mutations 必须携带原线上请求的完整非空操作组。

接口要求当前设备通过认证，并核对实例与世代；查询范围限定为当前工作区、当前世代。允许查询已撤销旧设备的回执，读取不依赖增量游标仍然有效。

服务端复用现有 operation 校验、mutations 规范化和 request_hash 算法，返回匹配的 applied、conflict、rejected 结果及原 versions/cursor；无记录返回 not_found；相同操作 ID 的载荷摘要不匹配返回明确错误并保留原 outbox，不把该错误当成 not_found 重新封装。该接口不执行写入，不补造回执，也不上传附件。请求体使用与 push 相同的 MAX_PUSH_BYTES 上限，不沿用认证接口的 4 KiB 限制。

**客户端推送与回执查询必须复用同一份线上载荷转换。** 当前 outbox 保存的是含正文的逻辑载荷，push_one 会把较长正文转换成 contentBlobHash/contentBlobSize，并可能对整个操作组启用正文分离。应提取确定性的转换函数，推送和查询采用完全相同的阈值、字段与 force_blob 规则；回执查询只转换并计算引用，不执行素材上传。直接提交未经转换的 outbox JSON，可能无法通过现有校验或匹配原摘要。

### 5.3 回执处理

| 查询结果 | 客户端动作 |
| --- | --- |
| applied | 按原 generations 确认已发送代次；已知远端版本只前进，不因旧回执倒退；保留发送期间产生的较新 dirty |
| conflict / rejected | 在同一事务中写入问题记录并移除已确定结果的冻结 outbox，保留 dirty、batch_id 和 generation，复用现有处理路径 |
| not_found，仍为原设备且游标有效 | 继续按原 operation_id 和原载荷重试 |
| not_found，设备已重登记或需要完整对账 | 获取当前同世代基线后，按下面的条件处理整个操作组 |

not_found 只表示查询时没有回执，不能据此认为旧请求永远不会生效。处理旧操作组时：

1. 如果所有目标实体的云端修订仍等于原 baseRevision，可为当前设备生成新 operation_id，但保留原 baseRevision 与冻结 mutations。新包及 origin_device_id、generations 在一次本地事务中替换旧 outbox，之后失败始终重试该新包。
2. 如果组内全部目标已经等价于原操作结果，可按已收敛确认原代次，并保留本地较新修改；删除等价性同时核对墓碑。
3. 如果云端已经推进且结果不同，在同一事务中写入整个操作组的问题记录并移除该冻结 outbox，保留原 dirty、batch_id 和 generation，进入冲突处理。不能为强行提交而把原 baseRevision 提高到最新值。
4. 多实体操作保持现有原子分组。部分目标已满足、部分目标不同的情况，按组处理，不拆成若干独立成功。

条件写入确保旧请求与重新封装的请求竞争同一个原始版本时，最多一个生效。收到新的冲突结果后重新核对状态，不以循环改包方式强推。

## 6. 同一世代的完整对账

### 6.1 区分重置原因

继续使用 HTTP 409 和 `error: "reset_required"`，增加 `reason` 字段，使旧客户端仍可识别既有错误，新客户端可选择处理动作。

| reason | 处理 |
| --- | --- |
| cursor_expired：cursor < min_cursor | 自动获取完整快照并对账 |
| cursor_ahead：cursor > head_cursor | 暂停推送，记录 history_inconsistent |
| instance_changed | 暂停，记录 identity_changed |
| epoch_changed | 暂停，记录 identity_changed |

缺少 reason 或 reason 无法识别的 reset_required 进入 legacy_review，保留本地状态，不自动推定为普通游标过期。

同世代快照中，已知实体的远端版本低于本地已知版本，或已知实体连墓碑都缺失，也属于历史不一致。现有服务端保留实体墓碑，此时不能把旧内容当作新对象自动上传。

### 6.2 区分首次合并与已有基线刷新

复用 `sync_progress.initialized`：

- false：首次接入，使用现有首次合并。
- true：已有共同基线，执行本节的完整对账。

复用 `sync_bootstrap` 暂存数据，`bootstrap_cursor` 非空表示完整快照和补拉已经完成。无论 initialized 是否为 true，exchange 看到完整待应用快照时，都先等待应用阶段，避免继续按旧游标推送。

下载阶段保留本地业务表、dirty、outbox 和 revisions。普通刷新不调用 queue_local_items，也不把所有本地对象重新标成待上传。

### 6.3 下载与应用顺序

1. 验证实例、世代和授权。
2. 对不确定 outbox 查询回执，按原代次处理已确认部分。
3. 下载完整快照，并补拉快照扫描期间的变化，复用现有水位及高版本覆盖规则。
4. 等待编辑器应用条件；隐藏期间允许保持下载完成、等待应用。
5. 应用前保存文稿和画布。进入数据库写事务后读取当时最新的 dirty 与 generation，不能沿用下载开始时的本地快照。
6. 完整校验版本、墓碑、引用和依赖后，按下表对账。
7. 在同一事务中提交业务变化、版本记录、问题记录和基线游标；删除已被完整快照覆盖、游标不大于快照最终水位的旧 sync_inbox，保留更晚记录；按当前本地代次与最新远端状态重算受影响的冲突，最后清理快照暂存。
8. 仍有可上传项时唤醒网络任务。

| 本地状态 | 云端相对已知版本 | 对账规则 |
| --- | --- | --- |
| 无本地修改 | 有更新或墓碑 | 应用云端变化 |
| 有本地修改 | 云端版本未变化 | 保留本地修改，继续以已知版本提交 |
| 有本地修改 | 云端也变化，内容不同 | 保存冲突，保留本地内容 |
| 有本地修改 | 云端目标已等价 | 只确认对应已发送代次，保留更晚修改 |
| 本地独有、没有远端版本记录 | 云端不存在同 ID | 保留并加入正常上传 |
| 云端独有 | 本地没有该实体 | 导入 |
| 已知远端实体 | 版本倒退或完整快照缺少实体及墓碑 | 记录历史不一致并暂停应用 |

发现历史不一致时先回滚业务对账事务，再用独立事务写入 paused 和 pause_reason。不能在随后返回错误而被回滚的同一事务中保存暂停状态。

有在途操作覆盖的实体先按第 5 节处理，不能绕过冻结操作独立改写其基线。没有在途操作时，可在应用事务内确认当前与云端等价的本地代次；存在在途操作时，只确认冻结代次，保留更晚编辑。

内容比较先补齐正文，并归一化 createdAt、updatedAt 及正文 blob 传输表示等非业务差异。删除等价依据实体标识和删除状态，不要求两端删除时间完全相同。

沿用现有按依赖顺序应用、引用重建和跨实体事务能力。目录与画布根据稳定 ID 对账；仅对真正独立新增的同名目录执行名称协调。云端删除目录、移动文章及删除画布引用时，按关联组验证，不以逐行覆盖造成引用悬空。

## 7. 暂停与人工恢复

在 `sync_binding` 增加 `pause_reason`，保留既有 paused 字段及读写兼容性。明确暂停原因：

| 原因 | 含义与处理 |
| --- | --- |
| backup_restored | 用户恢复了历史数据库；旧快照中的游标和操作不能直接视为本次新编辑 |
| identity_changed | 服务实例或同步世代变化；保留本地数据并核对目标服务 |
| history_inconsistent | 游标超前、修订倒退或墓碑历史不一致 |
| legacy_review | 升级前已暂停且无法确定来源，保留原处理入口 |

旧 paused=1 的行迁移为 legacy_review；正常行 pause_reason 为空。备份恢复流程写入 backup_restored。凭据失效显示需要授权，网络失败执行退避，同世代 cursor_expired 自动完整对账，这三类情况不写入人工恢复暂停。

既有 replace_baseline 保留在高级操作中，界面名称明确为“采用云端内容恢复本机”，继续展示实际影响并先生成恢复归档。用户主动执行后，云端内容决定当前工作区，本地独有文稿按既有规则进入废纸篓。

常规重装空库、正常新增设备、重新授权和同世代游标过期均不自动调用该操作。服务身份变化及历史数据库恢复继续保留现有显式处理边界，旧版本号不跨同步世代比较。

## 8. 应用进程内的后台同步

### 8.1 职责分配

网络调度放入 Rust 应用内任务，React 负责保存编辑缓冲、展示状态和安全应用远端数据。复用已有 Tauri 异步运行时、Tokio 定时器、Notify 和 SyncConnection.gate。

| Rust | React |
| --- | --- |
| 检查待上传数据、按时收发、处理回执、暂存快照与增量 | 文稿与画布保存、输入状态判断、调用 sync_apply、重新加载受影响内容 |
| 保留结构化运行状态与错误代码 | 订阅变化提示并重新读取状态 |
| 应用仍在运行时处理失焦、最小化和收起状态；按唤醒来源评估远端检查 | 窗口恢复后刷新本地状态、请求远端检查，并按既有条件尝试安全应用 |

在现有 main.rs setup 中启动一个网络任务，复用 Workspace、Assets、SyncConnection。将 sync_run 的核心交换提取为 IPC 与后台任务共用的函数，所有交换、连接、基线应用和冲突处理继续受同一个 gate 约束。

当前网页定时器中的收发职责迁入 Rust；单一网络调度器处理手动唤醒和后台计时。React 不再保留第二套网络定时循环。

采用原生调度的依据是当前产品支持窗口收起后继续运行。微软说明 WebView2 后台脚本计时器的实际唤醒受运行时和平台调度约束，因此网络任务不依赖隐藏页面的 setInterval；实现不需要调用文档中的预览版计时器设置 API。[资料](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2settings.preferredbackgroundtimerwakeinterval?view=webview2-dotnet-1.0.4071-prerelease)

### 8.2 调度规则

沿用现有节奏：5 秒检查、本地普通变更约 30 秒后上传、空闲时约 5 分钟检查远端，失败按现有有上限退避策略执行。前台恢复通过事件请求提前检查；定时参数继续采用当前值，后续根据双端实际可见延迟单独评估。

以下事件沿用立即唤醒交换的处理：

- 首次连接或重新授权成功。
- 用户点击“立即同步”。
- 基线或冲突处理应用成功，且产生可上传内容。
- 网络恢复通知。
- 收起前保存成功。

#### 前台恢复检查

前台恢复采用以下流程：

1. 在 `DesktopShell.tsx` 中，将窗口 `focus`、`blur` 与文档 `visibilitychange` 汇入同一前台状态判定。工作区从后台恢复为“可见且有焦点”时，请求一次远端检查；失焦或隐藏时更新状态，供下一次恢复判断。同一次恢复产生的重复事件合并处理。
2. 恢复时立即读取本地同步状态，尝试应用已经暂存的内容，并通过既有 `desktop.syncWake` / `sync_wake` 链路通知原生任务检查远端。请求远端检查的条件独立于编辑器能否立即应用数据。
3. 为现有唤醒链路补充“前台检查”来源，可采用可选来源参数。原生任务区分自动前台检查与既有立即唤醒；同批通知合并时，保留立即唤醒的执行语义。当前原生调度的立即唤醒会跳过 `retry_at`，因此前台来源需要独立遵守失败退避。
4. 前台检查优先复用现有 `next_pull`：原生任务收到请求时，将下次拉取时间提前到当前时刻，再按 `retry_at` 和既有执行条件判断。退避期间保留已经提前的时间；退避到期后，由现有 5 秒调度循环执行。成功交换后按原有规则安排下一次拉取。
5. 暂停、凭据缺失或已知被拒绝时，沿用相应状态和重新授权入口。退出中的工作区遵守既有生命周期。完整基线等待应用时，保留待检查状态，先完成当前基线的安全应用，再由现有调度继续处理。
6. 网络交换继续通过同一个 `SyncConnection.gate` 串行执行。远端变化进入持久化暂存区，文稿保存队列、输入状态及画布条件决定应用时机；窗口恢复不会强制覆盖编辑缓冲。

本次增量复用一个原生网络任务及已有调度时间字段，前端继续负责事件通知和安全应用。原生任务启动时的首次检查沿用当前流程。

初始化等待、鉴权失败、人工暂停和网络退避分别处理；其他设备尚在首次上传时显示等待进度，不要求用户变更连接方式。

原生任务只上传已经落库的内容。远端变化进入持久化暂存区，前端仍使用保存队列、画布状态和输入状态决定何时应用。正在编辑时可以继续收发，安全应用等到已有保存条件满足。

下载完成但尚未应用完整基线时，网络任务保留等待应用状态；不反复下载同一快照或持续空转。

### 8.3 收起与退出

当前窗口关闭到托盘的路径需要增加保存握手：

1. 原生关闭请求进入收起流程，通知 React 执行现有 flushWorkspaceForSync。
2. 等待全部文稿保存队列、画布写入和当前保存流程完成。
3. 保存成功后隐藏窗口，唤醒原生同步。
4. 保存失败时保持窗口可见，使用现有保存错误反馈。

收起后工作区继续处于运行状态，不调用 begin_exit。真正退出、数据库恢复和工作区关闭沿用既有生命周期，停止新交换并保留 outbox。

复用 Workspace.running_lifetime；开始退出时取消当前运行期。取消退出后重新取得新的运行期令牌并唤醒同步，不能在第一次取消后永久结束应用级调度循环。

最小化与失焦场景上传已保存内容；“刚输入就关闭到托盘”场景通过上述握手保证最后一次修改先落库。系统休眠期间不承诺执行，唤醒后继续处理持久化任务。

## 9. 状态与界面

复用 sync_status/sync_activity，统一返回本地状态快照：

- 绑定信息、初始化状态和暂停原因。
- 是否有可上传记录、是否有待应用数据。
- 冲突或被阻塞操作数量。
- 当前运行阶段及结构化错误代码。
- 当前会话最后一次完成交换的时间；重启后未检查时显示“等待检查”。

数据库已有进度与队列继续作为持久化依据；阶段和最近错误保存在同步运行状态中。事件通知前端重新读取；窗口恢复可见并获得焦点时，主动刷新本地状态，并按第 8.2 节请求远端检查。最近检查时间仍取实际成功交换记录，窗口恢复本身不代表同步完成。

| 显示状态 | 条件 |
| --- | --- |
| 未连接 | 没有绑定 |
| 需要重新连接 | 凭据缺失或被拒绝 |
| 正在连接 / 正在下载 / 正在合并 / 正在同步 | 对应步骤实际执行中 |
| 等待云端初始化 | 另一设备尚在首次上传 |
| 有内容待上传 | 存在可上传记录 |
| 已下载，等待应用 | 存在待应用快照或增量 |
| 有内容需要处理 | 存在冲突或阻塞问题 |
| 已暂停 | 存在明确人工处理原因 |
| 已同步 | 本会话完成过成功检查、初始化完成、没有待上传/待应用/冲突，并且没有正在运行或失败状态 |

现有 pending 会排除被问题记录阻塞的 dirty，因此 pending=false 不能单独用于判断“已同步”。“已同步”表示截至最近一次成功检查已完成当前可见工作，并保留最近检查时间。

设置页沿用 SettingRow、现有按钮与反馈位置。普通连接区不显示内部基线与初始化模式。设备管理提供复制连接信息、更换连接密钥和撤销设备，指定设备身份恢复及采用云端恢复本机放入高级操作。

非空首次接入时，将第 4.3 节的说明作为连接区域的辅助文字，沿用现有设置行说明样式，并与连接操作建立可访问关联。说明独立于成功、失败和运行进度反馈，连接仍使用原有按钮。空库接入与已有基线的普通重新授权沿用各自状态提示。
