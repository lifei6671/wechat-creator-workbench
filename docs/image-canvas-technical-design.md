# 图片无限画布编辑、拼接与云端同步技术方案

状态：已按获批的第二版原型实现，验证与平台范围见 [验收记录](image-canvas-validation.md)。采用统一画布，根据单选、多选和画板选区呈现工具。本文保留设计依据，不能替代实际验证记录。

编写日期：2026-11-28。现状依据当前仓库源码；外部组件在编写时核查，接入时重新确认发布版本和依赖兼容性。

## 1. 目标与首版范围

在正文图片的右键菜单提供「编辑图片」，打开接近全屏的图片编辑窗口。窗口以可平移、缩放的无限工作空间承载一个有明确导出边界的画板，兼顾单图美化和多图拼接。应用后，正文仍使用普通图片，可在另一台设备恢复图层继续编辑。

| 能力 | 首版范围 |
| --- | --- |
| 图片输入 | 自动载入右键图片；拖入文件、粘贴截图、从现有素材库添加多张图片 |
| 工作空间 | 平移、以指针位置为中心缩放、适应画板、单选、Shift 多选、框选 |
| 图层编辑 | 移动、等比缩放、输入宽高、裁剪、旋转、翻转、复制、删除、调整层级；提供位置输入及键盘微调 |
| 图片拼接 | 横向、纵向、宫格；调整顺序、统一尺寸、间距、外边距和对齐；拼接后仍可单独编辑各图 |
| 背景美化 | 透明、纯色、双色线性渐变、内置背景壁纸、自选背景图片；调整图片圆角和阴影 |
| 保存与输出 | 工程自动保存；应用到原图片位置；复制或另存画板成品；PNG、JPEG、WebP |
| 同步 | 工程草稿、原图、背景素材、已应用的不可变工程快照及成品图片；离线编辑后补同步 |

首版只提供一个导出画板。画板外可暂放图片，仍保存和同步，但不进入成品。增加图片不自动扩大已手工设定的画板；主动执行拼接时根据布局计算画板大小，超限则保留原布局并报错。

文字排版、绘图、AI 修图、自动识别长截图重叠、透视矫正、多画板、批量流水线和实时多人协作属于后续独立范围。GIF 首版按首帧参与合成，原文件保留，导出为静态图，导入时须明确呈现这一结果。

## 2. 现有能力与接入边界

| 能力 | 当前源码 | 接入要求 |
| --- | --- | --- |
| 图片右键菜单 | `apps/desktop/src/workspace/EditorContextMenu.tsx` | 新增编辑入口；只读、上传中及图片不可用状态按真实能力禁用 |
| 图片节点上下文 | `packages/editor-react/image-view.ts` 的 `ImageContext` | 已有 `isCurrent()`、`replaceSource()`；替换检查当前节点身份，不按 URL 批量替换 |
| 编辑器集成 | `packages/editor-react/index.tsx`、`workspace/Document.tsx`、`CollectionArticle.tsx`、`CanvasTextEditor.tsx` | 普通条目和专题内的文章编辑共用入口；专题临时文本仍需单独定义保存宿主 |
| 保存队列 | `apps/desktop/src/editor/save-queue.ts`、`src-tauri/src/content.rs` | 沿用版本校验与保存屏障，扩展图片应用事务，不能绕过正文保存队列 |
| 素材读取和导入 | `src-tauri/src/assets/commands.rs`、`assets/mod.rs` | 复用字节读取、校验和文件存储；补充工程私有输入及成品专用写入语义 |

| 素材身份与去重 | `assets/mod.rs` 的 `store_image` | 当前按哈希、来源键、类型复用素材记录；成品需保留独立逻辑身份 |
| 云同步 | `src-tauri/src/sync/contents*`、`apps/sync-server/src/*` | 复用操作组、版本、收据、冻结 outbox、依赖等待和按需下载；新增工程实体 |
| 资源保护 | `src-tauri/src/assets/cleanup.rs` | 纳入工程、成品快照、草稿、恢复记录、同步冲突及在途操作的素材引用 |
| 备份迁移 | `src-tauri/src/backup*` | 数据表随数据库备份；工作区迁移必须包含工程依赖图片，处理仅在云端的原图 |

现有专题画布使用 `@xyflow/react`，用于文章、文本和网页节点的组织；图片编辑需要像素裁剪、图层合成和精确导出，不复用专题节点表或将图片工程伪装为专题。窗口外壳、按钮反馈、文件选择、素材读取和生命周期可复用。

实施前同步协议为 2，实体白名单没有图片工程。本次升级为 3；协议上限保持：单实体 512 KiB、push 1 MiB、单操作组 256 个 mutation、blob 25 MiB。客户端图片还受 20 MiB 文件、单边 16000 像素、总计 4000 万像素约束。无限工作空间不解除这些输出和输入上限。

## 3. 渲染组件与职责

### 3.1 选型结论

优先采用 [Konva](https://github.com/konvajs/konva) 与 [react-konva](https://github.com/konvajs/react-konva)，按实际使用注册图片、矩形、分组和变换控件，按需加载编辑器。二者采用 MIT 许可证，接入时保留相应许可并纳入现有许可证清单。

| 方案 | 匹配情况 | 判断 |
| --- | --- | --- |
| Konva + react-konva | React 场景描述、图片变换、裁剪、命中、图层、导出及无限画布示例 | 首选；业务层实现拼接布局、保存和同步 |
| [Fabric.js](https://github.com/fabricjs/fabric.js) | MIT，提供 Canvas 对象模型和丰富编辑能力 | 可行，但本需求以 React 状态驱动和图片合成为主，首版不同时接入两套模型 |
| 现有 React Flow | 已有平移、缩放和节点组织 | 缺少图片编辑与像素导出所需能力，增加适配后收益有限 |
| 原生 Canvas 全部自研 | 可完成渲染 | 还需实现命中、变换框和多选，维护成本高于采用现有库 |

仓库 `package.json` 的 React 范围为 `^19.2.0`，当前锁文件解析到 19.3.1，不能仅凭声明断言运行时是 19.2。实施时按锁文件选定发布版 `react-konva`，验证其 React、react-dom、Konva peer dependencies；不使用上游主分支或无版本 CDN 作为生产依赖。本次不安装依赖或修改锁文件。

Pimg.app 用作[功能与交互参考](https://pimg.app/zh)，不据此推断其源码开放或复制其壁纸。内置壁纸使用本项目自制或已确认可再分发的素材；写入工程时转换为普通素材记录，避免不同客户端资源包版本导致效果变化。

### 3.2 分层

```text
图片右键菜单 → 图片编辑窗口
                  ├─ 工程状态：图层、画板、撤销与拼接参数
                  ├─ Konva：交互预览与独立导出场景
                  └─ desktop IPC
                       ├─ Rust 工程保存及版本检查
                       ├─ 素材文件与引用管理
                       ├─ 正文应用事务及恢复
                       └─ 现有私有云同步
```

React 工程状态是内容来源，不把 Konva 节点实例或完整节点树当作持久化格式。坐标统一采用画板像素单位；屏幕坐标通过视口变换换算。视口、选区、悬停、变换框和辅助线只属于本机交互状态。依据：[Konva 保存与撤销建议](https://konvajs.org/docs/data_and_serialization/Best_Practices.html)、[无限画布示例](https://konvajs.org/docs/sandbox/Infinite_Canvas.html)。

## 4. 交互与状态

### 4.1 打开和恢复

1. 捕获工作区、条目或宿主 ID、当前编辑器会话、图片节点上下文及原始地址，等待该宿主的保存队列完成。
2. 精确的 `asset://` 成品身份存在工程关联时，读取对应不可变快照，并查找针对该成品的未应用草稿；有草稿时恢复草稿，否则以成品快照开始。
3. 普通图片先通过现有原生读取接口取得字节并入库，再建立单图工程。初始画板与原图同尺寸，不默认增加装饰效果。
4. 原始输入草稿按「宿主 ID + 输入素材 ID」关联。首版同一宿主内相同输入素材共用这一未应用草稿；应用只替换本次右键节点，不替换其他相同图片。应用后的新成品 ID 自然区分后续编辑分支。
5. 工程主体恢复后再按需加载素材；缺失图片显示可定位的错误状态，不能用空白或其他图片替代并允许导出成功。

首版从普通文章、灵感、资料及专题内引用的实际条目接入。专题临时文本节点没有相同的条目保存契约，列为后续宿主适配，不在其右键菜单显示不可用的新入口；不影响已有图片操作。

### 4.2 窗口结构和可见元素

使用主窗口内的模态编辑层，不另开原生 WebView。保持操作空间，避免同时显示多列重复属性。以下为原型候选，实施前须按项目规则展示原型并获得批准。

| 区域与可见元素 | 最终用户需要它的原因 |
| --- | --- |
| 标题「编辑图片」与关闭按钮 | 明确当前任务，并返回正文 |
| 「添加图片」菜单中的「本地图片」「素材库」 | 使用已有素材或添加新素材，粘贴与拖放作为并行入口 |
| 「撤销」「重做」 | 恢复或重新执行画布内容修改 |
| 无限工作空间、画板边界及选区控件 | 区分可操作素材与实际输出范围 |
| 「横向」「纵向」「宫格」和拼接参数 | 快速排好多图并控制间距、顺序及对齐 |
| 单图属性中的位置、宽高、比例锁定、裁剪、旋转、翻转、层级 | 精确调整选中图片，提供拖动以外的操作路径 |
| 画板属性中的尺寸、背景、外边距 | 控制成品范围和整体外观 |
| 圆角、阴影设置 | 调整图片与背景的视觉关系 |
| 缩放比例和「适应画板」 | 在长图与大图中找回工作位置 |
| 「复制图片」「另存为」及格式设置 | 取得独立可用的成品 |
| 「应用到文章」或按宿主显示「应用到内容」 | 将当前成品放回发起编辑的位置 |
| 一处草稿保存状态及就近固定错误区 | 判断内容是否保存，并处理实际失败；同步进度沿用已有全局入口 |

控件采用 Radix Colors 语义令牌、0.5px 边框及最多三档字号，最小 12px。不增加装饰眉题、中点分隔、重复状态标签和操作教程。画布内容颜色是用户创作数据，支持自选颜色；编辑器界面的颜色按设计令牌处理，用户图片与壁纸不改色。

按钮遵循 [UI 规范](ui-design-guidelines.md) 5.5、5.6、6.3 节：任务处理中禁止同动作重复提交，等待真实完成，结果保留 1 秒；连续撤销和几何编辑不套用任务锁。成功无额外 Toast；失败使用固定区域的红字并保留输入。状态图标尊重减少动态效果，直接拖动不添加缓动。

### 4.3 键盘、保存和关闭

- Windows 使用 Ctrl，macOS 使用 Command 完成复制、粘贴、撤销和重做；空格拖动画布，方向键微调，Shift 多选。输入框聚焦时保留文本编辑语义，快捷键只在当前画布作用域生效。
- 裁剪或拖动中的 Esc 取消当前手势，再次 Esc 才尝试关闭编辑层。关闭前提交草稿；保存失败保留窗口与输入。关闭只退出编辑，不撤销已自动保存的草稿，也不自动应用正文。
- 拖动、缩放在手势结束时生成一个撤销项；滑块和连续数字输入合并为一次编辑。撤销栈只在当前会话保存，不同步每一步历史。
- 草稿采用每工程串行保存。手势结束及输入停止后提交内容快照，打开、关闭、切换宿主、同步应用、备份和退出都复用保存屏障；具体合并等待时间由交互验证确定，不按帧写库。
- 活跃编辑期间远端更新先持久化等待，不能重建当前画布覆盖手势或输入。保存屏障结束后再比较版本并应用或进入冲突流程。

## 5. 工程数据模型

### 5.1 内容格式

新增独立的、版本化的 `ImageScene`。首版包含 `schemaVersion: 1`、一个 `artboard` 以及有序 `layers`；保存业务数据，不保存 DOM、绝对路径、Blob URL 或图片 Base64。

| 对象 | 关键字段与语义 |
| --- | --- |
| 画板 | `width`、`height`、`background`、可选 `cornerRadius`；圆角缺省为 0，控制整个成品的外轮廓，宽高为正整数输出像素，画板外内容裁切 |
| 背景 | `transparent`、`solid`、`linear-gradient` 或 `image` 的判别联合；颜色、渐变角度/色标，或背景 `assetId` 及铺放参数 |
| 图片图层 | 稳定 `id`、`assetId`、`x/y`、`width/height`、`rotation`、`flipX/flipY`、`crop`、`cornerRadius`、`shadow` |
| 裁剪 | 原图固有像素坐标中的矩形；不改写原文件，旋转/翻转在裁剪后执行 |
| 图层顺序 | 数组从底到顶；多选仍保留稳定图层 ID |
| 拼接设置 | 当前排列顺序、模式、列数、尺寸策略、对齐、间距及外边距；布局结果直接写回图层几何 |

图片与背景使用稳定素材 ID；依赖的 `assetIds` 从场景派生，包括画板外图层。入口校验有限数值、合法裁剪范围、有效素材、类型白名单和序列化大小；内部绘制沿用已校验模型，不增加重复兜底。

### 5.2 本地表与同步实体

建议新增以下三张内容表，以及一张不参与同步的设备状态表。具体迁移编号在实施时按当前序列分配。

| 表 | 主要字段 | 作用 |
| --- | --- | --- |
| `image_projects` | `id`、`origin_entry_id`、`base_asset_id`、`scene_json`、`version`、`created_at`、`updated_at`、`deleted_at` | 可变工程草稿；origin 仅用于恢复入口，不建立删除父条目就级联删除工程的关系 |
| `image_renders` | `id`、`project_id`、`scene_json`、`scene_hash`、`output_asset_id`、`asset_ids_json`、`export_options_json`、`renderer_version`、`created_at` | 每次应用/持久化输出的不可变场景快照；不依赖工程当前草稿恢复旧成品 |
| `image_project_assets` | `project_id`、`asset_id` | 从当前草稿重建的引用索引，不单独同步；render 依赖从快照重建 |
| `image_editor_state` | `project_id`、本机视口和面板状态 | 本机设备偏好，不进入同步快照 |

新增同步实体 `image_project` 与 `image_render`。工程本地 `version` 用于写入并发检查，`remoteRevision` 继续由现有同步表维护，不能混用；`sceneHash` 对规范序列化后的场景计算，用于快照匹配，不替代实体版本。同步快照包含场景、来源关联、时间及派生素材清单，不传本地 `version`、文件路径或视口。

初始草稿 ID 由宿主 ID 和输入素材 ID 稳定派生，使两台设备同时从同一图片开始编辑时进入同一工程的版本冲突，而不是无声生成两个无法定位的草稿。明确另存副本时才分配新 ID，并在当前会话切换至副本；再次应用后的成品通过自己的 render 关联该副本。

`image_render` 的 ID 和输出素材 ID 一一对应。应用正文时先原子提交输出素材的 `asset://` 地址，默认图床上传及公开地址校验完成后自动回写图床链接。成品素材用专用来源键，例如 `image-render:<renderId>`，复用现有文件按哈希存储，同像素不同工程仍建立不同逻辑素材记录。不将工程关联写入图片 alt/title，也不通过哈希反推唯一工程。

`image_projects.base_asset_id` 是本次恢复草稿的输入成品或原图，不是草稿当前渲染结果。再次打开一个历史成品，优先恢复以它为输入的草稿；没有草稿则从该成品的不可变快照新建工程，不从其他成品的最新草稿猜测恢复。跨文章复用同一成品时复制工程作为当前文章草稿，原始文件共享，其他文章已应用的图保持不变。

`origin_entry_id` 不作为加载成品快照的必要条件；删除原文章或在另一篇使用成品后，仍能通过 `image_render` 恢复。工程删除使用墓碑，成品快照仍受正文、历史、其他工程及同步恢复引用保护；render 的工程来源允许指向已有墓碑，不要求草稿仍处于活跃状态。首版不增加自动删除所有历史快照的保留策略。

### 5.3 输入素材与公开地址

原图和自选背景通过专用的私有工程导入路径读取并入库，不因图床的自动上传配置立即公开。复用已存在且已公开的素材不会撤销原公开地址；新输入只同步到当前工作区的私有附件存储。

复用现有网络读取及 SVG 归一化边界，把外链先转成可校验字节。不能把可能被污染的跨域画布或远端 URL 作为唯一工程依赖。格式范围沿用素材服务，SVG 经现有流程转换为 PNG；不因为参考网站支持某格式就承诺项目也支持。

自动上传沿用现有队列、失败提示及公开内容哈希校验。图片工程成品的图床链接附带 `#wcb-image=<outputAssetId>`，片段不参与 HTTP 请求，仅用于保存精确的逻辑成品身份。回写不增加撤销记录，且只替换仍匹配的图片节点；上传失败或未启用自动上传时保留本地地址。

再次打开带标识的图床链接时，必须核对合法的输出素材 ID 及其不可变 render 快照，再从该素材读取原图与快照。片段是正文中的工程来源信息，与本地素材地址具有相同的工作区权限边界，不代表图片地址的认证；图床位置不参与工作区同步，因此工程恢复不依赖当前设备的地址缓存。同内容的不同成品依靠独立 ID 恢复，不能只凭哈希选择工程。没有标识的公开链接按普通图片处理；标识无效或依赖尚未同步时明确报错。公众号复制通过既有公开地址解析移除内部片段。原子应用后主动触发一次上传状态检查，涵盖相同内容早已上传、没有后续任务通知的情况。

Markdown 与 HTML 图片引用同时索引片段中的输出素材 ID，用于素材保留及同步依赖；普通图片公开地址仍按原规则归一化。代码片段中的示例链接不产生素材引用。

撤销和重做图片替换后重新检查上传状态。公开地址校验期间撤销应用时不得改写原图片；稍后重做会恢复回写，不依赖新的素材事件。

## 6. 拼接与渲染

### 6.1 拼接算法

拼接是对选中图层执行的一次可撤销布局操作，不提前压平成图片。顺序采用用户明确维护的选中图层顺序，初始沿用画布图层顺序；提供顺序调整操作，不以点击命中顺序作为隐含规则。

- 横向：统一裁剪后图片的显示高度，按宽高比计算宽度，沿 X 轴排列。
- 纵向：统一显示宽度，按宽高比计算高度，沿 Y 轴排列。
- 宫格：按指定列数生成等宽列；每行高度取该行缩放后最高图片，按所选方式垂直对齐。首版保持图片完整，不默认居中裁成同一比例。
- 默认统一尺寸以所选图片中的较小有效尺寸为基准，避免隐式放大；用户可修改目标尺寸。间距与外边距为非负画板像素，布局的亚像素坐标在导出时一致处理。
- 拼接会拟合选中图层并调整画板；未选中的图层保持位置，超出新画板的部分不导出。操作前后均可撤销，不偷偷删除未选中图层。

### 6.2 同一模型预览和导出

预览和导出使用同一场景解释器。背景、裁剪、圆角、旋转、阴影都实际绘制进成品，不依赖外层 CSS。独立导出场景只包含画板内容，排除视口变换、网格、选框、辅助线和界面主题。

导出固定以画板像素为基准，支持 1×、2×，倍率独立于窗口缩放及系统 DPI；依据 [Konva 高分辨率导出](https://konvajs.org/docs/data_and_serialization/High-Quality-Export.html)。输出倍率也计入尺寸和内存检查。PNG 默认，JPEG 遇透明背景时用导出面板中明确的底色合成；WebP 需校验实际编码 MIME，不能将 PNG 字节保存成 `.webp`。

渲染成功后，字节送入 Rust 素材边界再次检查格式、尺寸及 20 MiB 文件上限。校验失败保留工程，不能默默降低分辨率、切断长图或把失败标为应用成功。实际参与输出的原图缺失、下载失败、解码失败都阻止输出；画板外引用仍参与工程保存、同步和完整迁移。

工作空间只分配视口大小的 Canvas，通过坐标变换模拟无限范围，不创建覆盖全部世界坐标的巨幅位图。预览按可见内容管理解码与缓存，导出按输出范围、倍率及裁剪放大率解码原始素材，避免缩略拼图同时持有所有原图的全分辨率位图；结束后释放对象 URL、位图和临时渲染场景。首版限制每工程最多 100 张图层，作为可验证的产品容量，之后根据实测调整。

## 7. 应用到正文的一致性

### 7.1 保存协议

应用是本地操作，不等待网络恢复。建议增加工程保存、读取、成品准备及宿主应用 IPC；名称在实施时统一，不能直接用现有 `asset_import` 加普通正文异步保存拼成一个无事务流程。

1. 提交当前手势和草稿，排空宿主保存队列；捕获场景版本及哈希、宿主最新正文、期望正文版本、编辑器会话和目标图片身份。
2. 对冻结场景渲染，操作期间锁定重复应用及影响本次输出的画布修改。正文异步外部变化不能被锁定假定为不会发生。
3. 为本次应用分配并保留 render ID，将成品字节写入暂存或内容寻址文件区；此阶段文件可重用，但尚未宣称正文已应用。提交重试复用该 ID 与冻结参数，只有重新编辑并发起新的输出才分配新 ID。
4. 渲染完成后再次校验目标节点、工作区和宿主会话，生成仅替换该节点的 ProseMirror 事务及候选 Markdown。节点已删除、换源、宿主已关闭或只读时停止替换，保留工程并显示具体原因。
5. 在宿主保存队列内，以期望版本提交单个 Rust 数据库事务：登记成品素材与不可变快照、保存候选正文、重建引用、记录同步原子操作组。事务失败不改内存正文；文件暂存交由已有生命周期处理。重复提交相同 render ID 时核对提交回执，不能再次生成撤销项或推进正文版本。
6. 原生提交成功后，由同一保存协调器发布准备好的编辑器事务并更新已确认版本，形成一个正文撤销项，不再次触发旧正文保存。事务提交至内存确认的交接期间暂停相关编辑与同步回放；已有外部更新按版本契约处理。

必须为第 5、6 步实现明确的提交回执与会话交接，不能直接调用 `replaceSource()` 后宣称数据库与编辑器原子一致。渲染过程中崩溃恢复为未应用草稿；数据库提交后崩溃从已提交正文恢复。复用既有编辑恢复机制记录尚未确认的应用，禁止旧自动保存覆盖新正文。

### 7.2 撤销及多处引用

正文撤销只把该处图片恢复到原地址，重做恢复新成品；不删除工程、原图或成品快照。草稿内部撤销与正文撤销分开。相同图片出现多次时只更新右键的那一个节点。一个成品被多篇文章引用，重新编辑后生成新 ID，仅当前宿主选中位置改变。

复制成品和另存为不修改文章；输出仍登记同样的快照身份并保护素材。其云端操作组只包含成品素材和 render，不包含正文，工程与原图依赖先行。复制或文件保存的成功反馈以真实剪贴板/文件操作完成为准；取消文件选择不生成持久化 render。外部接收的软件只得到普通图片，不承诺带走工程。普通 HTML/Markdown 带图导出也只带成品；完整可编辑迁移使用工作区迁移包。

## 8. 云端同步

### 8.1 协议与存储

复用现有云服务的实体快照数据库和私有 blob 存储。Cloudflare 部署继续使用 D1/R2，自托管继续使用 SQLite/文件存储，不引入第二套图片工程服务、账户或公网素材桶。

新增两类实体的序列化、校验、快照、dirty 记录、bootstrap、增量回放、完整对账、依赖检查和冲突处理。服务端继续独立安装和构建，不引用 monorepo 外部源码。`image_project_assets` 及 render 引用从合法场景重建，不信任客户端任意填写的依赖清单。

首版场景 JSON 上限建议 384 KiB，分别约束草稿及 render 中场景，保留实体元数据和应用组余量；保存前仍以完整 UTF-8 载荷检查单实体及整组限制。继续复用文章长正文 blob 分流；不直接把工程 JSON 当成 `asset` 图片或绕过其 MIME 检查。超限保存明确失败并保留当前编辑，不增加大工程分片协议。

### 8.2 上传与下载顺序

1. 先在本地持久化输入素材、草稿及依赖引用，标记待同步，离线时继续编辑。
2. 原图、背景与成品字节按 SHA-256 上传，沿用大小和哈希校验。已存在的 blob 不重复传输。
3. 优先同步输入素材元数据及工程初始身份，使引用可解析；素材数量较多时可分批，未满足依赖的工程或应用组保留等待。
4. 草稿作为独立 `image_project` 同步。应用操作把成品 `asset`、不可变 `image_render` 和正文 `entry` 放入同一原子组，并以已经存在的工程和输入素材作为依赖。
5. 可变草稿不反复绑进正文应用组：render 已携带准确场景，之后继续编辑草稿不改变该快照，也不把后续几何保存与正文版本无谓耦合。若工程初始同步冲突，后续依赖组等待解决后再提交。
6. 另一台设备按组持久化并回放成品关联及正文，所引用 blob 必须已在云端确认登记；本机文件可按需下载。打开文章先取成品，打开编辑器再取原图和背景，素材未齐时禁止合成。

冻结 outbox 使用原有 operationId 和原载荷重试，不用最新草稿改写在途 render。服务端成功但客户端没收到回执时复用现有收据查询；重启后继续同一操作，不能重复创建成品或覆盖新版本。拉取仍以完整组落库和现有游标规则推进，不另设画布私有游标。

### 8.3 冲突

- `image_project` 整个场景为冲突单元，采用 `baseRevision`，不按更新时间最后写入获胜，不自动逐图层合并。
- 接入现有保留本地、采用云端和另存副本的交互能力；副本获得新工程 ID，输入文件共享。解决工程冲突不会修改已经应用的 render 或其他文章。
- 不可变 `image_render` 相同 ID、相同载荷可幂等确认；相同 ID 不同内容属于数据冲突，拒绝改写并保留可诊断记录。
- 正文应用组中的文章版本冲突时整组不部分落库，保留本地成品快照与工程供重试或副本使用。解决时沿用完整操作组处理，不只重放图片地址。
- 活跃编辑、未保存输入和未完成应用期间，远端场景不能自动覆盖本机画布；远端数据先持久化，待安全屏障后比较。

### 8.4 协议升级与已有设备

本方案建议协议从 2 升至 3，而不是在协议 2 下静默发送旧客户端不认识的实体。双方统一更新版本常量、请求头、meta 校验、契约测试及发行包协议标记；新旧不匹配沿用现有不兼容反馈并暂停同步，本地编辑与已有成品显示继续可用。

升级必须保留服务实例 ID、sync epoch、设备身份和凭据、认领状态、原有实体、操作收据、blob 与游标。不得通过重新认领或清空工作区完成迁移。服务端增量添加校验、关系约束和所需索引；本地迁移新增表及触发器，不改写原有图片。

实际迁移须验证已有冻结操作：原协议 2 的在途载荷在协议 3 中继续按原格式计算摘要并查询收据，已有字段和 operationId 不变化；未确认的老操作按升级后的接收规则继续完成。新实体只能在双方版本核对成功后推送。旧客户端访问新服务应得到明确的协议不兼容结果，不能半拉取后再失败。

部署顺序、所有设备升级及生产验收单独执行，本文不授权部署。旧应用回退只能读取旧成品，不能保证理解新数据库；回退前保存完整工作区迁移包并使用配套版本，不对新数据执行降级覆盖。

## 9. 引用、清理与备份

旧版本衍生成品的后续回收设计见[图片旧版本清理技术方案](image-version-cleanup-technical-design.md)，目前仅为草案，未改变本节的现有保护和清理实现。

资源保护闭包应包含：当前工程全部图层及背景、工程输入成品、被引用 render 的原始场景依赖、正文/封面/本地保留历史、编辑恢复、冲突副本、bootstrap/inbox/outbox 和正在输出的会话。

工程的 `base_asset_id` 可以指向旧成品，递归访问时按工程、render 和素材 ID 去重，防止重复扫描。新输出分配新 ID 且只引用已经存在的输入素材，render 一经登记不可改写，从写入顺序建立成品依赖关系，不另建通用图依赖框架。

工程从某篇文章解除关联不等于原图无人使用；render 也不能随原文章级联删除。用户删除图层时保留会话撤销所需图片，正常退出保存后再依据引用判断。沿用现有七天清理候选机制及按哈希组保护，同像素不同逻辑素材只要任一仍被引用就保留文件。

云端原图不因本机不再引用就删除，继续遵守当前同步资源的跨设备保护规则，不在本功能另造远端垃圾回收协议。数据库备份包含工程表但不因此变成图片字节备份；完整工作区迁移需补齐工程依赖的云端图片、校验哈希并打包。依赖不可下载时迁移失败且保留原工作区，不能产出声称完整的包。

### 11.2 云端与平台

使用隔离工作区和测试同步实例，覆盖 Cloudflare D1/R2 与 Node SQLite/文件存储；不得拿生产数据做清空、冲突注入或断网破坏性测试。

- Windows 建工程并应用，macOS 拉取后显示同一成品，恢复全部图层，修改后再回传 Windows。
- 两端同时离线改同一草稿，联网后保留双方，可选择版本或副本；文章成品不随草稿冲突自动改变。
- 中断 blob 上传、元数据提交、推送回执和分页拉取，重启恢复后无丢图、半组回放及重复成品。
- 已有协议 2 数据、收据和冻结操作升级；旧客户端被明确阻断；身份、epoch、游标及云端原图保持原值。
- 2× DPI 与多显示器、触控板缩放、Windows 右键、macOS Control-click、Command 快捷键及减少动态效果分别验收。浏览器自动化不能代替真实 WebView2/WKWebView 结果。
- 通过真实公众号编辑器粘贴、保存草稿、重新打开，确认成品背景及尺寸保留；导出成功不等于公众号验收通过。

性能样本至少包含 1 张 4K 图、20 张常规截图、100 张图层、1080×12000 长图以及接近现有总像素边界的输出。记录机器、平台、样本尺寸、首次加载、交互帧耗时、导出耗时和内存峰值。拖动目标为主流测试机约 16.7ms 帧预算，长图与大图重点检查不卡死、不崩溃和失败可恢复；这些是验收目标，尚无实测结论。

实施后按影响运行仓库已有 `pnpm typecheck`、相关 Vitest、必要的 `pnpm test`/`pnpm web:build`，以及 `cargo test --manifest-path src-tauri/Cargo.toml --locked`。同步服务执行 `npm --prefix apps/sync-server test`、配套契约及原生客户端验证；涉及 Tauri 新命令时核对 `main.rs`、`build.rs`、capabilities 三层注册。新增测试命令按实施时真实脚本填写，不预称已经存在。

实际产品验收状态见[验收记录](image-canvas-validation.md)，其中分别记录源码、自动回归、原生客户端、平台和部署范围。
